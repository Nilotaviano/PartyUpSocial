# Phase 6 — Polls: implementation design

Scope = the IMPLEMENTATION_PLAN Phase 6 row. The poll domain is already ratified — DOMAIN_MODEL §6 (aggregate, transitions, finalization), §7 (visibility incl. poll extenders), §10 (notification contracts) — and largely implemented and tested in Phase 1 (TRACEABILITY cites `Domain | 1` for D-070/D-079/D-080/D-088/D-119/D-131/D-140/D-153/D-155/D-164/D-170/D-171/D-172). This phase ships persistence, commands, jobs, HTTP, and web for that ratified model; nothing below re-decides domain behavior. **Citation namespace: a bare `§n` means DOMAIN_MODEL.md; spec sections are written `spec §n`; other docs are named.**

## 1. Persistence (S1)

- Tables: `polls`, `poll_options`, `poll_participants`, `poll_votes` — snake_case, `timestamptz ↔ Instant`, ids `Guid.CreateVersion7()` (A-015). `polls.status` is the materialized column (ARCHITECTURE materialized-status invariant); `deadline` and `selection_window_end` (= deadline + 48h, D-088) are stored, never derived in queries.
- DB-enforced uniqueness (logical uniqueness is constraints, not app checks), following the shipped two-partial-index ParticipantRef pattern (`SessionParticipationConfiguration.cs:36-37`):
  - `ux_poll_options (poll_id, start_time)` (D-080 merge probe under lock);
  - `poll_participants`: partial uniques `(poll_id, user_id) WHERE user_id IS NOT NULL` and `(poll_id, guest_identity_id) WHERE guest_identity_id IS NOT NULL`;
  - `poll_votes`: partial uniques `(option_id, user_id) WHERE user_id IS NOT NULL` and `(option_id, guest_identity_id) WHERE guest_identity_id IS NOT NULL`;
  - `join_requests`: **new** poll-side FK to `polls` plus partial unique `(poll_id, requester_user_id) WHERE status = 0 AND poll_id IS NOT NULL` (enum stored as int, matching the shipped session-side filter) — the shipped configuration (`JoinRequestConfiguration.cs:25`) carries only the session-filtered index today; this migration completes §5.3's "one open request per (target, user)" for the poll target.
- `poll_participants.first_response_at` nullable, write-once (D-172, §12-13) — aggregate-enforced, backed by `SET first_response_at = COALESCE(first_response_at, @now)`.
- **Retro-FK migration:** `sessions.origin_poll_id` shipped as a bare nullable column (`20260804154500_AddFixedTimeSessions.cs:63`, `SessionConfiguration.cs:29`) and `notifications.poll_id` likewise (`NotificationConfiguration.cs:42-43`) — there is no `Polls` DbSet yet. S1 adds the DbSet and BOTH FKs so the D-160 linkage and notification subject refs are DB-enforced, alongside the poll-side `guest_links` FK wiring (`guest_links` already model poll ownership + `ExpiredPoll` + re-parenting, §5.4); `guest_identities.poll_id` already carries the xor CHECK (`ck_guest_identities_target`) and gains its FK in the same migration.

## 2. Commands + locking (S2–S3)

All invariant-touching poll commands take the P3-LK-01 global lock order (users → friendships → blocks → session parents → poll parents → …); the poll row lock precedes every occupancy/option-count read.

- **Create** (registered organizer): ≥2 options and the 12-cap after dedupe at creation (D-080/D-131 — D-171 is specifically the *suggestion-time* cap error), instants ≤ creation+1y (§12-11), deadline choice ∈ {6,12,24,48} default 24 (D-070/D-131), non-private ⇒ ≥1 directly invited registered friend at creation (D-125); organizer PollParticipant + per-invitee invitation notifications in one A-016 transaction.
- **Mint / revoke / remove guests** (organizer; guests rename themselves — the D-125 private-guest-only arm): minting via `Poll.CreateGuestLink` (`Poll.cs:686-696`, using `GuestLink.CreateForPoll` at `:692`) is **`Polling`-only and pre-deadline** — `RequireVotingOpen` (`:1012`) throws otherwise, ratified by `PollGuestTests.CreateGuestLink_IsRejectedOnceVotingCloses_D079`; ≥256-bit CSPRNG, stored hashed, never logged (A-015). Revoking an **unclaimed** link → `RevokedByRemoval`; a claimed link cannot be revoked (`Poll.cs:776-780` Conflict) — the organizer instead removes the guest: `Poll.RemoveGuest` (`:742`, D-044, shipped + tested) removes the voter and revokes their link in one command. Renaming is **guest-side, not organizer-side** (D-044, PRODUCT_SPEC:536; DOMAIN_MODEL:105 gives the organizer remove + revoke only): `Poll.RenameGuest` (`:726`, keyed by `GuestLinkId` — the caller's own link) is exposed on the guest branch, mirroring the shipped `PUT /display-name` on the guest group (`GuestSessionEndpoints.cs:36`). Private polls may be created with zero registered invitees and links minted in the same transaction (spec §7.3: "created using only guest links").
- **Suggest option** (any Active voter incl. guests, D-033): guard `Polling ∧ now < Deadline`; lock → merge-or-cap-or-insert exactly per §6.2 (cap error = D-171); organizer-only notification, silent when the organizer suggests (§10).
- **Delete option** (organizer, `Polling|Closed`, silent, D-080/D-088): votes cascade; `FirstResponseAt` never recomputed (D-172); a zero-option poll can only be canceled or expire (§12-12).
- **Vote / revise** (Active participants incl. guests): guard `now < Deadline` (D-079); upsert per (option, participant); first submission sets `FirstResponseAt` (§12-13). Guest last-write-wins across devices (D-126) — no conflict check, lock still taken. Guests claim explicitly first (display name, §4) — an unclaimed link voting is a 409, mirroring the session contract.
- **Join request / approve**: window = `Polling ∧ now < Deadline` (D-118, `RequireVotingOpen` at `Poll.cs:576,619`); approval ⇒ Active PollParticipant with all current options (PRODUCT_SPEC:156,185). **Reject** is meaningful only while `Polling`: `RejectJoinRequest` (`Poll.cs:649`) applies due transitions first (`:652`), and every close path — Close, Cancel, Finalize, Expire — lapses pending requests (`:917-926` via `:346,:544,:913`), so after any close the request is already `Lapsed` and the route surfaces the invalid-transition error. No after-close reject semantics exist or are designed. Shared §5.3 pipeline, lapse-on-Close included.
- **Cancel** (organizer, pre-finalization): §6.1 row — links `RevokedByCancel`, requests lapse, D-166 notification.
- **Finalize** (organizer): the §6.4 nine-step atomic transition verbatim — clock-gated window, vote mapping (D-051; organizer Going regardless, D-155), deterministic allocation (`FirstResponseAt`, ParticipantRef id; §12-14), waitlist overflow (D-119), started/ended branches (D-153/D-164), guest re-parent with tokens preserved (§5.4), mute carry-over (§12-15), option-selected notification in every branch (§12-16), reminders only where still future (§9).

### 2.1 Block effects + deletion effects (the Phase 6 halves of the shipped executors)

- **Block scope (closes §12-39):** `IBlockEffectScopeProvider` is a single-implementation port (`IBlockEffectScopeProvider.cs:7-13`, registered at `DependencyInjection.cs:75`) — S3 **extends the concrete `SessionBlockEffectScopeProvider`, renaming it `BlockEffectScopeProvider`** (registration updated in the same commit), to load the poll scope after the session scope in one locked pass, preserving P3-LK-01's order (session parents before poll parents); a new `IPollLockRepository` port (mirror of the shipped session lock repository — none exists today) supplies `SELECT … FOR UPDATE` on poll rows. Scope: polls where either member of the pair organizes and the other holds a non-Removed PollParticipant → that participant → `Removed` (§4 item 3); either-direction open JoinRequests on the pair's polls → `Lapsed` (§4 item 4). The shipped domain already skips terminal polls **and** polls past their selection window (`BlockEffects.cs:116`, `now >= SelectionWindowEndsAt`) — the scope provider honors that exact gate rather than re-deriving one (note 7). **Materialization ruling:** pre-finalization poll removal produces *no* derived status event — a poll has no Confirmed-analogue for removal to flip; D-105's silence covers the removal itself, and the executor's event drain (an intentional safety, `BlockEffectsExecutor.cs:49-50`) stays exactly as shipped. The poll analogue of P4-NOTIFY-01 is an empty event set — a ruling, not a leftover.
- **Deletion scope (closes the empty `DeletionScopeProvider` poll list):** execution step 3 (§11, DOMAIN_MODEL:243) — the deleted user's PollParticipants in *others'* `Polling|Closed` polls → `Removed` (votes excluded from later finalization mapping, §6.3); their open poll JoinRequests → `Lapsed`; owned polls → Expire-by-deletion (§6.1, D-092) with D-170 notifications.

## 3. Jobs (S3)

Two Hangfire sweepers mirroring the session sweeper pattern (idempotent, shared transition functions; Hangfire present since Phase 4, A-013): **Close** at deadline (D-079) and **Expire** at selection-window end (D-088/D-170). The deadline-approaching notification (Deadline − 1h, D-120) is a scheduled emission keyed on the poll row, skipped if the poll has left `Polling` (§10).

## 4. HTTP surface (S4) — OpenAPI-first, no web-only conveniences

- `/api/v1/polls`: `POST /` · `GET /{id}` (voter-grid view: options, own votes, per-option tallies, roster through the masking service) · `POST /{id}/options` · `DELETE /{id}/options/{optionId}` · `PUT /{id}/options/{optionId}/vote` · `POST /{id}/finalize` (body: optionId) · `POST /{id}/cancel` · `POST /{id}/guest-links` + `DELETE /{id}/guest-links/{linkId}` · `GET /{id}/finalization-preview` (organizer; guarded by the **same clock-inclusive gate as Finalize** — now ≥ Deadline with a due Close applied first, now < Deadline+48h — never by materialized `Closed` alone, or preview would be refused in exactly the due-but-unswept window §6.1 promises never delays the organizer) · poll-nested join-request routes mirroring the session shape (`SessionEndpoints.cs:97-130`): `POST /{id}/join-requests` (request) · `DELETE /{id}/join-requests/mine` (withdraw) · `GET /{id}/join-requests` (organizer list — the `ListPollJoinRequests` analogue) · `POST /{id}/join-requests/{requestId}/approve` · `POST /{id}/join-requests/{requestId}/reject` · `POST /{id}/guests/{guestIdentityId}/remove` (D-044) · `GET /polls` (§4.1).
- **Guest arm (D-125/D-114), joining the shipped shape without touching it:** the `/g/{token}` exchange gains a poll branch and still redirects to the one `/guest/{linkId}` SPA route; the cookie stays path-scoped to `/api/v1/guest/{guestLinkId}`. The shipped `GET …/session` (flat `GuestSessionResponse`, `JsonUnmappedMemberHandling.Disallow` — `GuestSessionEndpoints.cs:22-24`, `GuestSessionContracts.cs:23`) is a frozen mobile contract and is **not** modified: polls get parallel nested resources on the same `MapGroup` — `GET …/poll` (flat `GuestPollResponse`: poll, options, own votes, and the same masked per-voter grid data the registered view gets (D-030 individual responses; participant-identical, unlike the roster-less GuestSessionResponse) — participant-identical, D-030/D-114; the registered roster view carries `GuestIdentityId` per the shipped precedent `SessionContracts.cs:252,356`, so the remove route's key is obtainable), `POST …/poll/claim` (display name required, §5.4/D-017 — claiming is explicit; a vote before claim is a 409 enforced at the **application layer** — Poll's claimed-guest guard is private to the aggregate, unlike the session's aggregate-enforced check, and no new domain entry point is added for it), `PUT …/poll/options/{optionId}/vote`, `POST …/poll/options` (suggest), `PUT …/poll/display-name` (guest renames themselves — D-044's guest arm). A session-typed credential on a poll route (or vice versa) is a 404 — fail closed. Terminal-state notices per §5.4 (`ExpiredPoll` included).
- **Poll guest credential:** the shipped protector payload is session-typed under purpose `PartyUp.Sessions.GuestLinkCredential.v1` (`GuestLinkCredentialProtector.cs`) with a non-nullable `SessionId`; rather than version that contract, S4 adds a **parallel poll protector** — purpose `PartyUp.Polls.GuestLinkCredential.v1`, payload (GuestLinkId, PollId, Mode, IssuedAt, ExpiresAt) — so session tokens are structurally unreadable on poll routes and vice versa. Lifetime clamp: active-mode expiry = `selection_window_end` (after which the poll is terminal); terminal-notice mode reuses the shipped bounded terminal lifetime. **After finalization re-parents the link (§5.4, tokens preserved):** a held poll credential no longer matches a poll-owned link → poll routes return the finalized notice (state + created session id; no re-exchange URL field — the server stores only the token hash and cannot reconstruct the `/g/{token}` link, so the client renders "re-open your invitation link" copy instead), and re-exchanging the preserved raw token now mints a *session* credential for the same link. No silent cookie upgrade. Registered reads/writes resolve through the visibility engine extended with the §7 poll rules (extenders = organizer + Active registered participants except all-Unavailable voters, §12-17) and fail closed (404).
- Problem codes follow the shipped problem-details convention the Phase 5 availability endpoints use (namespaced codes + flat `errors` fallback): `poll_not_found`, `poll_option_cap`, `poll_voting_closed`, `poll_selection_window_closed`, `poll_zero_options`, ….

### 4.1 Poll list + discovery (owner ruling 2026-08-08: ships)

`GET /polls` returns two bands: **involved** — §7 rule-1 access, status ∈ {Polling, Closed} (Finalized polls are reached from their session, D-160; Expired/Canceled excluded, §1) — and **discoverable** — non-private `Polling` polls visible through §7 rule-2 inherited access: the D-118 join-request entry point (PRODUCT_SPEC:156,185), built on the shipped Discover pipeline pattern. Both bands use A-072 cursor pagination.

### 4.2 Shipped conventions these routes join (binding)

- **Antiforgery:** every unsafe endpoint (POST/PUT/DELETE, registered and guest alike) requires the `X-CSRF-TOKEN` header per the shipped convention.
- **Rate limiting:** `RateLimitTests.cs:122` pins **26 dimensions**; the operation map (`:31-109`) must stay exhaustive. Poll guest ops (`ClaimGuestPollLink`, `VoteOnPollAsGuest`, `SuggestPollOptionAsGuest`, `RenameGuestPollIdentity`) join the shipped `guest-write` dimension (`:90`); registered ops arrive as **four new user-partitioned dimensions** a poll-local grouping (the session split differs: session-write holds request/withdraw, session-attach only approve/reject/promote) — `poll-write` (CreatePoll, CancelPoll, DeletePollOption, CreatePollGuestLinks, RevokePollGuestLink, RemovePollGuest), `poll-attach` (FinalizePoll, ApprovePollJoinRequest, RejectPollJoinRequest, RequestPollJoin, WithdrawPollJoinRequest, ListPollJoinRequests), `poll-vote` (VoteOnPollOption, SuggestPollOption), `poll-list-read` (ListPolls, GetPollFinalizationPreview) — the pin updates 26 → 30 (four new dimensions; guest ops add operation ids to an existing dimension, not a new one) with the map, in the same commit as each endpoint lands (the disclosed-extension precedent the availability dimensions set).
- **Pagination:** A-072 cursors on both `GET /polls` bands — no offset paging.
- **i18n:** every new user-facing string ships in en, pt-BR, es in the same commit (key-parity gate); times render through the shipped locale formatters.

## 5. Web (S5–S7) — Tabletop Club tokens (PHASE5_1_DESIGN binding)

- **Voting grid — the second a11y hotspot.** Options as rows (start time via `Intl.DateTimeFormat`; elapsed options visibly ordinary — D-140), each row a **radiogroup of three vote controls** (Available/Maybe/Unavailable) on the shipped APG idiom (roving tabindex + arrow keys; ThemeToggle precedent); the page is NOT an ARIA grid — independent radiogroups outperform composite grids in screen readers. Control accessible name: "{option time}, {value}"; per-option tally as plain text ("3 available · 1 maybe"); voter disclosure renders through the masking service (blocked/tombstone → Anonymous User, ordinary styling, D-076/D-086).
- **Vote-state marks — value never color-alone, selection never fill-alone.** Value glyphs always rendered, aria-hidden (the accessible name carries the value): Available = free pair + `✓`, **Maybe = maybe pair + `?` (owner ruling 2026-08-08)**, Unavailable = busy pair + `✕`. **Selected state** (`aria-checked`) = the value fill **plus a 2px inset `ink` ring** — the Phase 5.1 selection idiom — because the availability fills read <3:1 against card in both themes and cannot carry checkedness alone; unselected controls are card-filled with the glyph in `ink-soft`. Pairs (all PHASE5_1_DESIGN §1-ratified): free/free-ink 7.21/7.63 · maybe/maybe-ink 6.21/7.86 · busy/busy-ink 6.47/6.32 · ring `ink` vs each fill ≥5:1 both themes. Accent-*filled* elements in dark keep the PHASE5_1_DESIGN dark-block rule (`accent-ink` border).
- **Poll create** mirrors SessionCreatePage (token forms, kit Dialog discard guard D-162); option editor with inline creation-cap error (D-080/D-131) and dedupe-as-merge feedback (D-080); suggestion-time cap error is D-171's.
- **Poll detail** states: Polling (live grid + suggest + deadline as text), closed-awaiting-selection — entered by the same clock-inclusive gate as Finalize, not materialized status (grid frozen; organizer selection controls with per-option preview), Finalized (link to the session, D-160), Expired/Canceled (terminal notices). **Preview guarantee (exact):** preview and finalization share one mapping/allocation function — identical inputs give identical outputs; a shown preview can still differ from the outcome when inputs legitimately change in between (option deleted in `Closed`, a participant Removed by block or deletion). No stronger claim is made.
- **Prefill poll arm (D-102/D-163, A-083 pattern):** each recommended window yields one option instant via the shipped `RecommendationPrefill.ForPollOption` (`RecommendationPrefill.cs:73,84` — a `PollOptionPrefill` carries one `StartTime` + a clamped flag; duration is not an option property, spec §7.3-1); the client accumulates selected windows into `/polls/new?startTimes=…` (repeated param) with the clamp surfaced not silent, route query only, never a server draft (D-152/D-162); §12-11's ceiling re-validated server-side.
- **Calendar/Home wiring — an OpenAPI change, planned as one:** `CalendarPollOptionView` is an *empty* record today (`CalendarContracts.cs:10`); **S4** fills it (poll id, title, option instants, own-vote summary), reruns `gen:api` against the running API, and updates `CalendarEndpointTests.cs:182-184` plus the D-111 traceability row in the same commit. S7 binds the calendar `pollOptions` layer + Home polls band to the data; the pollOptions legend swatch shipped in 5.1 becomes truthful.
- **Guest voting page** extends the `/guest/{linkId}` page with the pollView branch (explicit claim with display-name capture, last-write-wins D-126, terminal notices). The organizer's poll detail gains the guest-management panel from SessionDetailPage's idiom: mint/copy links, revoke unclaimed links, and **remove guest** (D-044 — the only way to detach a claimed guest voter, since claimed links refuse revocation); renaming stays with the guest on their own page.

## 7. Interpretation notes (spec-silent points resolved here, §12-style)

1. **Vote submission is per option, not per ballot.** The spec never defines a batch submit; `FirstResponseAt` = first single vote upsert. A "submit all" UI affordance issues per-option calls; partial failure leaves earlier votes standing.
2. **Deadline countdown renders as text** (no live region): announced on load and focus; the Deadline − 1h notification (D-120) is the reminder channel, not the UI.
3. **Preview shares finalization's mapping/allocation function** — same inputs ⇒ same output; divergence only through legitimate input changes between preview and finalize (§5).
4. **`GET /polls` involved-band scope** = §7 rule-1 access in {Polling, Closed}; Finalized reached via its session (D-160); Expired/Canceled excluded (§1). Discoverable band = §7 rule-2 non-private `Polling` polls (the D-118 entry point).
5. **Guest link minting window** is the shipped `Polling`-and-pre-deadline gate (`RequireVotingOpen`) — a link minted before the deadline stays `Active` through `Closed` and re-parents on finalization (§5.4); no new links after voting closes.
6. **“Non-finalized” (§11 step 3, DOMAIN_MODEL:243) is read as `Polling|Closed`:** the other non-finalized statuses are terminal, where §1's terminal-state gate already forbids mutation — removing there would be dead work.
7. **The block scope's skip gate is the shipped one** (`BlockEffects.cs:116`): terminal polls and polls past `SelectionWindowEndsAt` are skipped — §4 item 3's unqualified wording is narrowed because such polls have no live capacity, extender set, or finalization mapping for a `Removed` row to affect.

No new D-numbers are required; every behavior above traces to an existing decision or a numbered note here.
