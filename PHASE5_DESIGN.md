| **A-075** | **Availability has no occupancy invariant; its serialization points are the owner's `users` row then the touched `availability_series` rows.** Overlaps are legal and merged at read time, so `DOMAIN_MODEL.md:16`'s parent-lock-before-occupancy rule does not extend here; what needs serialization is multi-table *structural* editing (split, series delete, zone migration). Every availability write locks the owner's `users` row (`FOR NO KEY UPDATE`, A-069), then series, then blocks, then skips — one `SELECT … FOR NO KEY UPDATE` statement per table carrying its declared `ORDER BY`, order imposed by Postgres, never by a C# comparer. A write that provably touches no rows in a given table (e.g. a block create touches no series) omits that table's statement; it never reorders the ones it does issue. **`DOMAIN_MODEL.md:16`'s global order gains one tail:** users → friendships → blocks → session parents → poll parents → `availability_series` → `availability_blocks` → `availability_occurrence_skips`. | **A-076** | **Recurrence expansion, merging and overlap ranking are Domain-pure and never re-expressed in SQL.** The read repository returns raw rows (one-time blocks intersecting the window; series whose `[EffectiveFrom, EffectiveUntil)` intersects it; their skips) plus each owner's current `TimeZone`; Application calls `AvailabilityProjection.Project` per owner and `OverlapEngine.FindWindows` once. The ratified semantics are wall-clock `LocalDateTime` arithmetic through a lenient DST resolver with gap-collapse and a tzdb fallback (§12-19, §12-29) — not expressible in `timestamptz` arithmetic without forking the engine. **Series-window seam:** `effective_from`/`effective_until` are `date` in the *series'* zone while the requested window is `timestamptz`. Converting them in SQL would need the series zone and is forbidden by this ruling, so the repository **over-fetches with a fixed three-day pad on each side** and lets `AvailabilityProjection` discard occurrences outside the true window. Mandated predicate: `effective_from < ((@to AT TIME ZONE 'UTC')::date + 3) AND (effective_until IS NULL OR effective_until > ((@from AT TIME ZONE 'UTC')::date - 3))`. The explicit `AT TIME ZONE 'UTC'` is mandatory: a bare `::date` cast resolves under the session's `TimeZone` GUC. **Pad = 3 days**, because an occurrence of series-local date `d` is live across `[M(d) − 14h, M(d) + 60h)` (UTC+14 00:00 start; UTC−12 23:45 start plus the maximum `Duration15` of 24h, `src/PartyUp.Domain/Kernel/Duration15.cs:10`), so no smaller pad is sound on the trailing side. Gate: `AvailabilityWindowPadTests` (S2, §4.2/§11). **Corollary:** a series duration is persisted as `duration_minutes integer` and reconstructed as `Duration15`, never as Postgres `interval` — `interval` is a (months, days, microseconds) triple whose round trip is not value-stable on a 15-minute grid. | `DOMAIN_MODEL.md:195`, `:199`, §12-19/§12-29; `ARCHITECTURE.md:54`. |

### 3.1 Required `DOMAIN_MODEL.md` §12 notes (next free number 44; three added, §12-44..§12-46)

Only genuinely ambiguous points are ratified; nothing that restates an existing note or another document.

- **§12-44 — A viewer who is busy in a window neither removes nor downranks that window.** Once the viewer's own blocks are loaded for the calendar `myAvailability` layer, subtracting or penalising windows the viewer cannot personally attend is forbidden. A window where every selected friend is free and the viewer is busy ranks exactly as it would if the viewer were free, because `PRODUCT_SPEC.md:196` makes the organizer's judgement final and Phase 5 ships no conflict detection at all (§1.2). The viewer's blocks are a calendar layer for context; they never reach `OverlapEngine`.
- **§12-45 — Availability of an owner the viewer cannot read is EXCLUDED, never masked.** Roster masking exists because a hidden participant still holds capacity effects (`DOMAIN_MODEL.md:189`); availability has no roster, so an "Anonymous User is free Tuesday" row would both disclose that a person exists and corrupt the D-035/D-052 Available/Maybe counts. Exclusion happens in `ReadableOwners` before projection (A-078).
- **§12-46 — A requested availability or calendar range longer than 92 days is refused, not truncated.** §12-27 states the 92-day bound for *overlap* queries. Phase 5 adds two range-scoped reads that the spec does not cover — `GET /calendar` and `GET /me/availability` — and they take the identical bound and the identical `range_too_large` refusal (§8). Refusal, never silent truncation: a truncated calendar is indistinguishable from an empty one.

### 4.2 Round-trip and constraint gates (real Postgres)

Create an owner with one-time blocks (one materialized from an edit-one carrying provenance), two series (one open-ended, one bounded), and skips; save; clear the context; reload; prove semantic equality of instants, `IsoDayOfWeek`, `LocalTime`, `Duration15`, zone id, effective range, provenance. Each of these must fail **at the database boundary**: off-grid start, a duration outside 15..1440 or not a multiple of 15, `effective_until < effective_from`, half-filled provenance, duplicate skip PK. A series whose `zone_id` is absent from the tzdb still loads and expands via the owner's current zone (§12-29).

**Window-pad gates (`AvailabilityWindowPadTests`, the A-076 named S2 gate).** The boundary cases the pad exists for, each fetched-and-then-discarded correctly rather than silently missing: (a) *trailing* — a series in UTC−12 with `effective_from = d`, `effective_until = d+1`, start 23:45 and a 24h `Duration15`, whose occurrence is live in UTC until `d+2 11:45`, is returned for a window starting `d+2 06:00`; (b) *leading* — a series in UTC+14 with `effective_from = d` and start 00:00, live from `d−1 10:00` UTC, is returned for a window ending `d−1 12:00`; (c) a series whose rows the pad admits but whose occurrences all fall outside the true window contributes **zero** occurrences after projection; (d) the same two boundary series appear in `/calendar`, `/me/availability` and an overlap search alike, since all three go through the one read.

**DST gates, against real Postgres in this slice** (not delegated to Phase 1): a spring-forward occurrence collapses and is dropped; a fall-back occurrence is longer in real time; a 23:00→01:00 series carries into the next day and never wraps; one northern- and one southern-hemisphere zone each round-trip and expand correctly (§12-19, `DOMAIN_MODEL.md:195`).

## 5. Application

### 5.1 Ports and read models

Two new ports. Each is **declared and registered in the slice that supplies its implementation, never earlier** (`PHASE4_DESIGN.md:156`: "A DI registration ships in the slice that supplies the implementation, never earlier"; declaring an unimplemented port is legal C#, registering one is a compile error). Both ports' first implementation lands in S2 with the schema, and **each is re-opened by its consuming slice** — S3 for the write port, S4 for the read port — because a signature has no proof until a caller and a gate test exercise it (§12 serialization).

One method rather than three keeps the four reads inside a single repository call so they cannot be issued at different points in time; A-079's budget and the S2 bridge gate are phrased in **statements** for that reason.

**`DOMAIN_MODEL.md:189`'s two render rules are two distinct signals, and the read model keeps them distinct.** Both render as the Anonymous User string client-side (`SessionDetailPage.tsx:506`, `web/src/i18n/en/sessions.json:61`), but they differ on the wire, so a null display name alone cannot carry both:

1. **Tombstoned owner → null name for every viewer (D-092).** Wire shape is **unchanged from what shipped**: `displayName` omitted, `userId` **present**. `User.MarkDeleted` already nulls `users.display_name` (`User.cs:406`), so the repository projection alone carries this rule and no lifecycle flag is round-tripped. 2. **Blocked pair → masked between the two only (D-076).** Wire shape is `displayName` omitted **and `userId` omitted**: an id the viewer can correlate across sessions defeats the masking, which is the same no-id rule `MaskedParticipant` (§8.1) states. Rule 4 of the A-077 fragment does not reach this case (A-077 (e)) — on a third-party session the pair legitimately coexists with access intact. Attendance, waitlist position and occupancy are untouched.

**The masking decision is a read-model field, not an inference from a null name.** `RosterEntry` (`SessionReadModels.cs:27-34`) gains **`bool MaskedForViewer`**, set to `true` **only** by the use case applying rule 2 and never by the repository — S4 owns both the field and its only writer. It cannot be replaced by nulling the participant id: `RosterEntry.Participant` is a `ParticipantRef`, which admits no reference carrying neither a user id nor a guest identity id (`src/PartyUp.Domain/Kernel/ParticipantRef.cs:26-36`), so the id is structurally always there (§2). A masked entry keeps its real `ParticipantRef` — occupancy, ordering and the deletion executor all still see the true participant — and only the response drops it.

**Contract shape (S5).** `RosterEntryResponse.From` (`SessionContracts.cs:244-252`) maps `MaskedForViewer == true` to `UserId = null`, and `RosterEntryResponse.UserId` gains `JsonIgnore(WhenWritingNull)` so the property is **absent**, not null, on a masked entry. The same attribute makes `userId` absent on guest rows, whose `userId` was always null and whose identity is already carried by `guestIdentityId` — an omission a generated client reads as `undefined` where it read `null`, with no shipped consumer either way. `ParticipationId` is unaffected: it is per-session and grants no cross-session correlation, which is what lets the client key a masked row (§11, S7).

**Join-request paths carry no masking, and the two `JoinRequestViewResponse.From` overloads differ only in what they can resolve.** A blocked pair can never reach a join request at all — rule 4 denies the blocked viewer access to the session before a request can be opened — and the organizer is entitled to the identity of someone requesting to join their own session. So `requesterId` stays present on both overloads, and the added `requester: MaskedParticipant` is populated **only** on the summary overload (`SessionContracts.cs:351`), which is the one with a resolved `RequesterDisplayName`; on the 201 create overload (`:344-349`, whose sole recipient is the requester naming themselves, `SessionEndpoints.cs:704`) the field is omitted, because a create result carries no name resolution and inventing one would mean a second read on the write path.

**The block-pair lookup adds no port member: the masking use cases reuse the shipped `IBlockRepository.FindPairsAmongAsync`.** It is already the set-based both-direction read of every block row between the viewer and a candidate set, and `SessionReadUseCases` already calls it on the detail path to build the `Viewer`'s `blockedIds` before `FindDetailAsync` (`SessionReadUseCases.cs:83-88`). A second member over the same table with the same predicate would be indirection with one implementation (A-003, the same reuse argument A-081 makes for the zone migration), so S4 masks from that call's result and S2 adds nothing here.

The masking use cases are `SessionReadUseCases` (upcoming/history/detail), `ListDiscoverableSessionsUseCase`, `GetActionableInboxUseCase` and `GetCalendarViewUseCase`, all in S4's write set. **No masking in SQL, no `IdentityMasking` call site** — `IdentityMasking` has no production caller today and Phase 5 does not become its first; the two rules above are the whole of `DOMAIN_MODEL.md:189` for the surfaces Phase 5 renders.

### 5.2 Use cases

`CreateAvailabilityBlock`, `EditAvailabilityBlock`, `DeleteAvailabilityBlock`, `CreateAvailabilitySeries`, `DeleteAvailabilitySeries`, `DeleteAvailabilityOccurrence`, `EditAvailabilityOccurrence`, `ReadMyAvailability`, `FindOverlapWindows`, `GetHomeSuggestions`, `GetCalendarView`, `ListDiscoverableSessions`, `GetActionableInbox` (D-103 region 1, §5.1), plus the A-081 step in `ChangeTimeZoneUseCase`. Each is a thin transaction wrapper over Phase 1 pure code. The two carrying structure:

- **`EditAvailabilityOccurrence`** dispatches on scope. `onlyThis` **branches on whether the occurrence has already been edited**, because `AvailabilitySeriesEditor.EditOccurrence` unconditionally returns a fresh skip plus a fresh materialized block (`AvailabilitySeriesEditor.cs:17-23`) and `AvailabilitySeries.EnsureOccurrenceDate` never consults skips (`AvailabilitySeries.cs:133-141`), so calling it twice on one date either violates the §4.1 skip PK or duplicates the block. The use case therefore inspects the rows the step-4 locks returned (`FindSkip`/`FindMaterializedBlock`, §5.1 — in memory, no second `SELECT`):
  - **No skip** — the first edit: `EditOccurrence` writes one skip and one materialized block (the D-134/D-143 default).
  - **Skip and its materialized block both present** — a re-edit: the existing block is **rescheduled in place** (`AvailabilityBlock.Reschedule`, the shipped method the block-edit path already uses), and no second skip is written. The outcome is `200` with the same `AvailabilityBlockView`, whose `blockId` is unchanged, mirroring the idempotent repeated delete-one (§8, `DELETE …/occurrences/{occurrenceDate}`). Re-editing an occurrence means moving the window the user already moved; it never mints a second artifact for one date.
  - **Skip present, block absent** — the occurrence was deleted (delete-one, or a delete of the materialized block): `404 occurrence_not_found`. There is no occurrence left to edit, and the response is identical to a date the series never covered, which is the §8 indistinguishability default. Re-creating that window is `POST /me/availability/blocks`, not a PATCH.

  **No Domain change is required and none is made** — every branch is composed from shipped Phase 1 members (A-076); the branch itself is adapter logic and lives in `AvailabilityOccurrenceUseCases.cs` (S3's write set). `thisAndFuture` → `SplitFromOccurrence` → source `EffectiveUntil` = the occurrence date (exclusive), successor from that date, and every skip and materialized block dated ≥ the split is **dropped, never migrated** (§12-20). When `SeriesSplitResult.OriginalBecameEmpty` is true the original row is **deleted**, so no zero-length series is persisted. One transaction under P5-LK-01.
- **`FindOverlapWindows`** resolves the selection (omitted = all accepted friends, D-110), filters through `AvailabilityVisibility.ReadableOwners` (A-078, §12-45), validates the range with `EnsureRangeAllowed`, defaulting an omitted range to `OverlapEngine.DefaultRange(clock)` (D-108/§12-27), reads raw rows, projects each owner **in that owner's zone**, and calls `OverlapEngine.FindWindows` once. `GetHomeSuggestions` is the same path with the all-friends selection and `OverlapEngine.HomeSuggestions` applied last (D-116/D-136) — never a second ranking.

## 6. Locking, visibility, Discover

### 6.1 `P5-LK-01` sequence

Every step 2-4 statement is one `SELECT … FOR NO KEY UPDATE` carrying its table's A-075 `ORDER BY`; the mode and the order are stated once, in A-075.

1. Authorize the owner (`AvailabilityVisibility.CanWrite`); a non-owner target is 404, never 403.
2. **Lock the owner's `users` row.** This is the write's serialization point (`P5-LK-01`); every later statement runs with the owner's availability quiesced.
3. Lock the touched `availability_series` rows (`WHERE id = ANY(@ids)`, or `WHERE owner_id = @ownerId` where the set is derived).
4. Lock the affected children — **4a.** `availability_blocks` (the target block, or every materialized block whose `source_series_id` is a locked series), then **4b.** `availability_occurrence_skips` of the locked series. A write that provably touches neither table omits both statements; **a plain block create therefore locks `users` alone** and manufactures no zero-row lock to keep the count uniform. A write never issues its statements out of order.
5. Re-validate **after** the locks: grid, range order, series still present, occurrence still inside `[EffectiveFrom, EffectiveUntil)`, and — for `onlyThis` — whether a skip already exists for `(series, date)` (§5.2).
6. Apply the Phase 1 editor, persist, commit.

Required outcomes are `P5-LK-01`'s, and each holds because of step 2 rather than because of a child-table lock. One addition here: zone migration versus block edit serializes at step 2 and leaves the block's absolute instants unchanged either way (§12-21) — with the A-081 mode mismatch on `users` (`FOR UPDATE` on the profile path) still conflicting, so serialization holds under the A-069 retry.
