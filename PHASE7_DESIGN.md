# Phase 7 — Notification transports + preferences: implementation design

Scope = the IMPLEMENTATION_PLAN Phase 7 row (`IMPLEMENTATION_PLAN.md:128-135`). Emission is done: transactional `Notification` rows already commit with every owning mutation (A-016; `SessionNotificationMaterializer`, `PollNotificationMaterializer`, `SendFriendRequestUseCase`, `ImportSteamFriendsUseCase`, `PollDeadlineApproachingJob`), recipients are the ratified §10 contracts, write-time mute is applied (§9, D-090/D-113), and the reminder scheduler is shipped whole (`session_reminder_handoffs` + `SessionReminderDueJob`, A-066). This phase adds **transport, read/unread, and the preference surface**, and reinterprets nothing: D-105's silence and D-122/D-123's edit-notice split are untouched. **Citation namespace: a bare `§n` means DOMAIN_MODEL.md; spec sections are written `spec §n`; other docs are named.**

## 1. Persistence (S1)

- **`push_subscriptions`** — the first table for the shape-only Phase 1 entity (`src/PartyUp.Domain/Notifications/PushSubscription.cs`): `id` (Guid v7), `user_id` FK Restrict, `channel` (smallint, `WebPush = 0`; native APNs/FCM append members without a shape change), `endpoint` (≤2048), `public_key`, `auth_secret`, `created_at`, `revoked_at?`. Partial unique `ux_push_subscriptions_active_endpoint (user_id, channel, endpoint_hash) WHERE revoked_at IS NULL`, with `endpoint_hash` (SHA-256 hex) an **EF shadow property** written by the repository adapter, on the `NotificationConfiguration.ReminderHandoffId` shadow precedent — the Domain entity keeps its ratified shape.
- **A-015 posture for these columns:** `endpoint` and `auth_secret` grant push access, so A-015's *token* discipline would hash them — but unlike a guest link, which is only ever *verified*, they must be **replayed verbatim** on every send and therefore ship plaintext by necessity. The binding compensations: they are never logged (dispatch failures log outcome and subscription id only), never returned by any read contract, and purged with the user (§11 step 5). `id` remains a Guid v7 entity id and grants nothing.
- **`notification_push_sends`** — the send-log: `notification_id` FK, `push_subscription_id` FK, `claimed_at`, `outcome` (smallint Claimed/Delivered/Gone/Failed). **No `attempts` column** — nothing retries a claimed send (§3's eviction rule), so an attempt counter would record a number no code ever reads. **`ux_notification_push_sends_once (notification_id, push_subscription_id)`** is the whole idempotency mechanism — a DB constraint, never an app check (ARCHITECTURE §3), reached only through `INSERT … ON CONFLICT DO NOTHING RETURNING id`. No payload column ever.
- **`notifications.dispatch_state`** — smallint, default `Pending(0)`, terminal `Dispatched(1)` / `Skipped(2)`, with partial index `ix_notifications_dispatch_pending (created_at, id) WHERE dispatch_state = 0`. The migration **backfills every existing row to `Skipped`**, so shipping Phase 7 cannot replay months of history as a push storm. The column is an EF shadow property, not a `Notification` member (§9 — structured refs only, `:204`).
- **Unread keyset index** `ix_notifications_unread (recipient_user_id, created_at DESC, id DESC) WHERE read_at IS NULL` serves both the count and the `scope=unread` cursor page; the shipped `ix_notifications_recipient_created` already serves `scope=all`.
- **Poll-side mute uniqueness:** `NotificationMuteConfiguration.cs:23` ships only `ux_notification_mutes_session_user (session_id, user_id) WHERE session_id IS NOT NULL`. S1 adds its twin, `ux_notification_mutes_poll_user (poll_id, user_id) WHERE poll_id IS NOT NULL`, completing the xor target's logical uniqueness in the DB. `ix_sessions_origin_poll_id (origin_poll_id) WHERE origin_poll_id IS NOT NULL` lands here too — it is what makes §3's third mute arm an index lookup rather than a scan.
- **Deletion — §11 step 5's whole declared scope:** `UserDataScope.PushSubscriptions` (`DeletionExecutionResult.cs:20`) becomes real, and the step's `NotificationMute` purge lands beside it — subscriptions, send-log rows, and mute rows all removed in the same transaction, ahead of the `notifications` purge `INotificationRepository.DeleteForRecipientAsync` already performs.

## 2. Notification read projection (S2)

Masking is **not** rebuilt here: `IdentityMasking.ForUser` (`src/PartyUp.Domain/Visibility/IdentityMasking.cs:19`) is DOMAIN_MODEL §7's one rendering service, already ordering tombstone → blocked pair → named and already carrying the third outcome `MaskingReason.ProfileIncomplete` (`:61`). What is missing is a **notification-actor read projection** that consumes it — the shipped consumers (`SessionReadUseCases.MaskBlockedPairRoster`, its poll twin) project roster rows, and a notification actor is not a roster row.

S2 adds `NotificationReadUseCases` + `NotificationReadModels` in `src/PartyUp.Application/Notifications/`. Per row it resolves the actor's `MaskedIdentity` via `IdentityMasking.ForUser(actor, viewer)`, the subject's title, and the structured instants the type needs — `OptionStartTime` for `PollOptionSuggested (14)` and `PollOptionSelected (19)`. Render inputs are the recipient's `Locale` **and** `TimeZone`: every instant renders in the recipient's own zone (D-060, spec §8.5), which server-side rendering must supply because no client is present at delivery. A user with neither set falls back to `en` through the shipped `EmbeddedEmailTemplateRenderer.CanonicalizeLocale` (`:35`) and to UTC.

**Subject access is re-resolved per row (the gate this projection cannot omit).** Blocking deletes no notification rows, and §7 rule 4 (`DOMAIN_MODEL.md:186`) makes the pair's session or poll *nonexistent* for the viewer — so a row whose subject the viewer can no longer reach must not leak the subject's current title (post-block edits included) or a deep link that answers 404. Blocking is only the loudest case: a viewer who left the roster, was `Removed`, or whose inherited access lapsed reaches the same state without any block. The projection therefore resolves each row's subject through the visibility engine at read **and** at dispatch time:

- **no access ⇒ the row renders in its masked minimal form**: type, an Anonymous actor, `createdAt`/`readAt` — no subject title, no subject id on the wire, no link. It stays in the list and still counts as unread; this is render-time masking on top of a real record, not access denial (D-086's boundary).
- **no access ⇒ dispatch marks the row `Skipped`**, unsent: a push that cannot name its subject or link anywhere carries nothing.

## 3. Dispatch (S3)

**The `notifications` table is the outbox.** No second outbox table: a notification row is already the durable, committed, structured record of one (event, recipient) pair (§9), and A-016 requires only that the *record* be transactional — an in-process post-commit continuation is what a deploy kills.

- **`PushDispatchJob`** — Hangfire recurring, `Cron.Minutely`, `[DisableConcurrentExecution(timeoutInSeconds: 55)]`, registered in `RecurringJobRegistrationService` beside the four shipped jobs (A-066 cadence contract). It pages `dispatch_state = 0` ordered `(created_at, id)` — **no time bound in the predicate**, so every Pending row is reached and leaves the index.
- **Per-row outcome, and what flips the state.** A paged row resolves to exactly one terminal transition before the next tick: past the lateness ceiling ⇒ `Skipped` (ruling 6); muted ⇒ `Skipped`; subject unreachable (§2) ⇒ `Skipped`; no active subscription ⇒ `Dispatched` with zero sends; otherwise fan out, then **one UPDATE sets `Dispatched`** once every live subscription of that recipient carries a send-log row. **A claim loser sends nothing and writes no outcome** — the existing row is what completes coverage. This is also the resolution of the crash case: a row claimed but never outcome-written re-pages next tick, its send-log rows are found to already cover every live subscription, and it transitions to `Dispatched` **without sending**. No row re-pages forever, and no crash produces a second delivery. A subscription created *after* a row reached `Dispatched` never receives that row — coverage is evaluated once, at the same lateness semantics ruling 6 governs.
- **Mute is re-checked at dispatch time.** Write-time mute (§9) cannot cover a mute created *after* the record — including during a Pending backlog — and D-090/D-113 suppress the push, not merely the record. **The join must survive finalization**, which re-parents a poll mute onto the created session (`AttachToSession`) and leaves the notification row's `poll_id` pointing at a poll no mute references. The predicate is `mute.user_id = n.recipient_user_id` **and** any of: `mute.poll_id = n.poll_id`; `mute.session_id = n.session_id` (the types carrying both refs, e.g. `PollOptionSelected (19)`); `mute.session_id ∈ (SELECT id FROM sessions WHERE origin_poll_id = n.poll_id)` — the shipped D-160 linkage (`Session.OriginPollId`), index-backed per §1. **`SessionReminder` (type 12) is exempt**, the same single exception the write path carries (D-090, `ReminderRules`); the in-app row is never altered either way.
- **Transaction boundary.** The claim insert **commits before** the HTTP send; the outcome write is a second transaction keyed on the send-log row id, so re-writing it is idempotent. Delivery is **at-most-once per (notification, subscription)**, which is exactly the trade `IMPLEMENTATION_PLAN.md:133` names ("duplicates must be swallowed, late delivery accepted").
- **Concurrency.** `DisableConcurrentExecution` serializes ticks, but a rolling deploy's overlapping containers and lock-timeout expiry both leave two workers legitimately able to reach one notification; the unique constraint — not the lock — is the guarantee, so exactly one insert wins per (notification, subscription). Proven by a concurrent-worker integration test mirroring `ReminderDueJobTests.ConcurrentWorkers_CreateExactlyOneReminderNotification_D082`.
- **Eviction.** `404`/`410 Gone` → `PushSubscription.Revoke` (already idempotent) + outcome `Gone`; `429`/`5xx` → `Failed`, subscription untouched, no retry; `400`/`413` → `Failed`, logged **without endpoint, keys, or payload**.
- **`PushSendLogPruneJob`** — daily recurring, deletes send-log rows older than 30 days; past the lateness ceiling nothing can re-dispatch, so those rows serve debugging only.
- **Package (A-013 unlock):** `Lib.Net.Http.WebPush` in `Directory.Packages.props`; the binding requirement is RFC 8291 `aes128gcm` plus RFC 8292 VAPID, so a substitute satisfying both is a mechanical swap of the `IPushSender` adapter. `IPushSender` is **channel-scoped, not universal**: a native channel adds a sibling adapter selected by `push_subscriptions.channel`, rather than widening this one.
- **Transport seam:** `Push:Provider` ∈ {`log`, `webpush`}, selected in `DependencyInjection` exactly as the shipped `Email:Provider` switch is (`DependencyInjection.cs:170-180`). `LoggingPushSender` is Development-only (it throws otherwise, as `LoggingEmailSender.cs:15-19` does) and writes one JSON file per send to `Push:DropPath` (default `push-drop/`) — the mail-drop analogue the browser lane asserts against.

### 3.1 Payload

Payloads carry `{title, body, url, tag}` and are built from the §2 projection for that recipient, so masking and the subject-access gate both apply before the payload exists (ruling 5). Text comes from embedded per-locale resources keyed `PartyUp.Application.Push.Templates.{NotificationType}.{locale}.{part}` through the shipped `EmbeddedEmailTemplateRenderer` idiom (`:17,:35`). `tag` = `"{session|poll|friend}:{subjectId}"` (ruling 2); `url` is the SPA deep link (`/sessions/{id}`, `/polls/{id}`, `/friends`). ARCHITECTURE:78 makes this the server-side recipient-locale mechanism; the pt-BR/es *quality* pass is Phase 8's.

## 4. HTTP surface (S4) — OpenAPI-first, mobile contract

| Operation id | Route |
|---|---|
| `GetPushConfig` | `GET /api/v1/push/config` → `{ vapidPublicKey, pushEnabled }` — authenticated registered users only (no anonymous read); the public key is public by construction |
| `CreatePushSubscription` | `POST /api/v1/push/subscriptions` (`{ channel, endpoint, publicKey, authSecret }`) — idempotent upsert on (user, channel, endpoint hash) that **also updates rotated `publicKey`/`authSecret`** on the active row; returns `{ id }`. A channel other than `webpush` is `400 push_channel_unsupported`; VAPID unset is `409 push_not_configured` |
| `DeletePushSubscription` | `DELETE /api/v1/push/subscriptions/{subscriptionId}` — idempotent 204. An id that is unknown **or** belongs to another user returns the identical `404 push_subscription_not_found` (fail closed) |
| `ListNotifications` | `GET /api/v1/notifications?scope=all\|unread` — A-072 cursors under two distinct scope names, `notifications-all` and `notifications-unread`, so a cursor crossing scopes is `400 invalid_cursor`; sortKey `created_at` desc then `id` desc |
| `GetUnreadNotificationCount` | `GET /api/v1/notifications/unread-count` |
| `MarkNotificationRead` | `POST /api/v1/notifications/{notificationId}/read` — idempotent, keeps the first `ReadAt`; an unknown or another user's id is `404 notification_not_found` |
| `MarkAllNotificationsRead` | `POST /api/v1/notifications/read-all` — idempotent; marks as read every row that is unread at call time |
| `MuteSession` / `UnmuteSession` | `PUT` / `DELETE /api/v1/sessions/{sessionId}/mute` (D-090/D-113) |
| `MutePoll` / `UnmutePoll` | `PUT` / `DELETE /api/v1/polls/{pollId}/mute` |

- **Masked-actor wire rule (exact, per `SessionContracts.cs:251-253`'s `JsonIgnoreCondition.WhenWritingNull` precedent — the field is *absent*, not null):** a blocked-pair-masked actor omits **both** `actorUserId` and `actorDisplayName`; a tombstoned or profile-incomplete actor keeps `actorUserId` and omits `actorDisplayName`, which the client renders as Anonymous User. The §2 minimal form likewise omits the subject id and title rather than nulling them. Center rows and any actor-bearing payload field follow this identically.
- **Mute write path (this slice's Application half):** `SetNotificationMuteUseCase` + `INotificationMuteRepository` (`Add`/`RemoveForTarget`), backed by the two partial uniques of §1. Who may mute = anyone the visibility engine grants access to the target; no access ⇒ 404 (`session_not_found` / `poll_not_found`, unchanged). Idempotent in both directions.
- **Mute after finalization — no second, inert poll-keyed row.** `PollDetailResponse.muted` on a **Finalized** poll reads through the re-parented row, resolved by `Session.OriginPollId`, and the mute toggle is **disabled on every terminal poll** (Finalized/Expired/Canceled): the live control lives on the created session's detail page. `MutePoll` on a terminal poll is refused with the shipped `poll_invalid_transition` code — no new code. **`UnmutePoll` on a Finalized poll is not refused**: it removes the re-parented row through the same `OriginPollId` resolution, so `muted` reads false afterwards on both the poll and its session; on an Expired or Canceled poll it removes the poll-keyed row directly.
- **Reminder-default replan (closes a live D-082 gap):** `SetReminderDefaultUseCase` (`src/PartyUp.Application/Profile/SetReminderDefaultUseCase.cs`) today only writes `user.SetReminderDefault` — it is not among `ISessionReminderHandoffWriter`'s **seven** callers (`CreateSessionUseCase`, `EditSessionUseCase`, `SessionInvitationUseCases`, `SessionJoinRequestUseCases`, `SessionParticipationUseCases`, `SetSessionReminderUseCase`, `FinalizePollUseCase`) — so a 1 h → 24 h change leaves every existing handoff at the old instant, and at fire time `ReminderRules.Plan` returns a now-past instant the job reads as *cancel*: the user silently gets no reminder. S4 extends the use case to page that user's future non-terminal sessions where they hold an eligible participation, in pages of 100 until exhausted, taking the shipped lock order per session — `LockUsersAsync` then `LockSessionsAsync` (`SetSessionReminderUseCase.cs:35-36`, A-066) — and to call `ReplanAsync` per session.
  - **The new offset is passed explicitly, not read back.** `ISessionReminderHandoffWriter.ReplanAsync` gains an optional account-default parameter, because the user mutation is still untracked-unsaved inside the delegate (`IUnitOfWork.ExecuteAsync` saves after it) and a writer that re-reads the projection would recompute against the **old** default — the same read-ordering hazard the codebase already documents at `FinalizePollUseCase.cs:106-109`. An explicit parameter is ordering-independent; a flush-before-replan is not. The port change lands in its shipped implementation `SessionReminderHandoffStore.cs` and in the interface's test fake (`SessionCommandTransactionTests.cs:129`); the page itself is a new `ISessionRepository.ListFutureSessionsWithEligibleParticipationAsync(userId, afterCursor, limit)` read.
- **`MyProfileResponse` gains `pushPromptEligible`** (`MeEndpoints.cs:930-950`) — the server-derived half of ruling 4, computed per request as a single `EXISTS` over the caller's own participation, invitation and join-request rows (no cache, no stored flag). A field on an existing operation, so the op-id set grows by the **eleven** ids above and no more; `gen:api` still reruns.
- **Losing the client-side subscription id is recoverable without a second route:** re-POSTing the same endpoint returns the existing subscription's `id`, which the client then `DELETE`s.
- `PUT /me/reminder-default` (`MeEndpoints.cs:44`) and `PUT /sessions/{id}/my-reminder` (`SessionEndpoints.cs:147`, D-082) already ship; no new reminder routes.
- **Guests (D-167):** none of these routes exist on the guest `MapGroup`; a guest credential reaches no notification or push surface, and holds no channel at any layer.
- **Shipped inventories this phase extends (disclosed-extension precedent):** every unsafe route requires `X-CSRF-TOKEN` and joins the antiforgery equality inventory; the rate-limit dimension map goes **30 → 33** — `notification-read` (`ListNotifications`, `GetUnreadNotificationCount`, `GetPushConfig`), `notification-write` (`MarkNotificationRead`, `MarkAllNotificationsRead`, `MuteSession`, `UnmuteSession`, `MutePoll`, `UnmutePoll`), `push-subscribe` (`CreatePushSubscription`, `DeletePushSubscription`), all user-partitioned, pinned in `RateLimitTests`; the closed problem-code inventory gains `notification_not_found`, `push_subscription_not_found`, `push_not_configured`, `push_channel_unsupported`.

## 5. Web (S5–S6) — Tabletop Club tokens (PHASE5_1_DESIGN binding)

- **Notification center** at `/notifications`, plus a bell in the app chrome carrying the unread badge. The list is flat and reverse-chronological (ruling 2), cursor-paged, each row linking to its subject deep link — **except a §2 minimal-form row, which renders unlinked** — with a per-row **Mark read** control and a header **Mark all read**; unread rows are marked by a dot glyph **and** a bold-weight title, never color alone (PHASE5_1_DESIGN §3, `:53`), and their accessible name states "unread". ## 6. Browser lane

New routes join `AuditedRoutes` in the slice that ships them (`/notifications` in S5, `/settings/notifications` in S6) and are audited by axe in **both themes**, zero exclusions. The lane is black-box and out-of-process (`PlaywrightFixture` spawns the API), so the push proof needs a spawned-process trigger seam, not an in-process call: `PushDispatchTriggerService`, a `PeriodicTimer` hosted service (the A-037 precedent) registered **only when `Push:DispatchIntervalSeconds` is set**, ticking the same job class through its own scope. S6 edits `PlaywrightFixture` to spawn the API with that key at 2 s, beside the existing `RateLimits__RegisterPerIpPerHour` override it already passes in both topologies (`PlaywrightFixture.cs:48,183,248`); production never sets it and keeps the minutely Hangfire cadence. ## 8. Configuration and secrets (owner-provisioned)

`Push__Vapid__PublicKey`, `Push__Vapid__PrivateKey`, `Push__Vapid__Subject` (a `mailto:`), and `Push__Provider` reach the container through `deploy/compose.yaml` env from the VM's `.env`, as `Email__*`/`Google__*` do (`compose.yaml:42-48`). The private key is a secret: never in the repo, never in logs, never in an OpenAPI example (A-015). Absent or partial configuration ⇒ `pushEnabled=false`, `CreatePushSubscription` answers `409 push_not_configured`, the dispatch job no-ops, and every user sits on the D-175 in-app path. **Owner action:** generate the keypair and set the four variables on the VM.

## 9. Rulings (spec §8.4's "to be decided", resolved here)

1. **Unread state.** `ReadAt` is set only by an explicit `MarkNotificationRead` / `MarkAllNotificationsRead` — neither opening the center nor clicking a push marks anything read. The badge is the exact count of `read_at IS NULL`, displayed `99+` above 99.
2. **Grouping is a tray concern, not a list concern.** Collapsing happens in the OS tray via the per-subject `tag` with `renotify: false`; the center list is flat, with no server-side digest or grouped record.
3. **User preferences are exactly three controls** — per-browser push on/off, account default reminder (D-082), per-session/poll mute (D-090/D-113). A per-type opt-out matrix would be a new product decision, not an interpretation.
4. **Prompt state is split by what it describes.** *Whether the user has completed a D-147 qualifying action* — sending a session or poll invitation, creating a session, RSVPing, or requesting to join one — is an account fact, derived server-side and carried by `pushPromptEligible`, so a second device does not restart the qualification. *Whether this browser has been asked, dismissed, or enabled* is per-device browser-local state (the D-181 client-preference precedent), because permission and subscriptions are per browser install.
5. **A push payload may contain nothing its recipient could not read through `GET /notifications`** — it is built from that recipient's own gated, masked projection (§2), is never persisted, and is never logged. No payload-free fetch-on-click variant is designed.
6. **Lateness ceiling — 24 h, owner-ratified 2026-08-09.** A Pending notification older than 24 h is marked `Skipped` unsent (a push about a session that already started is noise; the center still carries the row). This narrows `IMPLEMENTATION_PLAN.md:133`'s "late delivery accepted" to a bounded window by owner decision: the ceiling is what keeps the send-log's 30-day retention (ruling 8) and the `Dispatched`-once coverage rule coherent, and it bounds the backlog that accumulates while VAPID is still unconfigured (§8).
7. **The send-log key** the plan row states as (event, recipient, channel) is realized as `(notification_id, push_subscription_id)`: a notification row already *is* one (event, recipient) pair, and a subscription is one channel instance.
8. **Send-log retention is 30 days.**

No new D-numbers are required; every behavior above traces to an existing decision or a ruling here.
