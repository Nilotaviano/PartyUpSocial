## 1. Scope, non-scope, and exit criteria

### 1.1 In scope

Phase 4 delivers direct fixed-time sessions end to end: create/edit, registered and guest invitations, RSVP, join request/approval/withdrawal, waitlist promotion/rejection, materialized status transitions, cancellation, upcoming and Completed-history reads, all session notifications as transactional in-app rows, durable reminder handoff, Hangfire maintenance, guest bearer-link exchange, real block/deletion session effects, OpenAPI and generated web types, and accessible localized web routes. This is the plan's Phase 4 promise (`IMPLEMENTATION_PLAN.md:86-96`).

It implements D-005, D-006, D-007, D-010, D-011, D-012, D-017, D-018, D-019, D-020, D-021, D-038, D-039, D-040, D-041, D-043, D-044, D-046, D-047, D-048, D-053, D-055, D-056, D-057, D-058, D-062, D-063, D-065, D-074, D-075, D-076, D-077, D-081, D-082, D-084, D-085, D-086, D-089, D-090, D-091, D-092, D-095, D-098, D-099, D-105, D-106, D-107, D-112, D-113, D-114, D-115, D-121, D-122, D-123, D-124, D-125, D-126, D-129, D-130, D-141, D-142, D-150, D-152, D-156, D-157, D-162, D-164, D-166, D-167, D-168, D-169, D-173, D-174, and D-176. The list is enumerated rather than expressed as ranges because D-045 and D-054 are Superseded comment rules (`TRACEABILITY.md:72`, `TRACEABILITY.md:81`) and must not be swept in.

"Implements" is not "newly proves". Section 12's owner cells list only the D-numbers that gain **new** Phase 4 test citations in `TRACEABILITY.md`; section 11 names those tests. A D-number may appear in two owner cells when two layers each add real evidence (for example D-130 at the command layer and at the HTTP layer); it may never appear in an owner cell without a section 11 test that names it.

### 1.2 Explicitly not in scope

Poll creation/voting/finalization and poll jobs remain Phase 6; availability, calendar and Discover remain Phase 5. No recurring sessions, named groups, comments, actual-attendance tracking, guest-account reconciliation, duplicate-guest-name rule, catalog synchronization, or platform catalog client is added.

**Reminder and mute boundary against Phase 7.** The plan gives Phase 7 "per-session mute (D-090, D-113); reminder preference Off/15m/.../24h, default 1h (D-082); reminder delivery job" (`IMPLEMENTATION_PLAN.md:118`) while giving Phase 4 "notification emission complete for all §8.4 session events (in-app channel live)" and `P4-REMIND-01` (`IMPLEMENTATION_PLAN.md:90-91`). The reconciliation is by channel, not by event:

- Phase 4 owns the in-app channel end to end, which includes the reminder **record**: the durable handoff, the replan/cancel triggers, and the job that writes the in-app reminder notification row. Phase 4 also honors D-090/D-113 at write time (a muted recipient gets no row at all; the reminder is the sole mute exception per `DOMAIN_MODEL.md:206`), and honors D-082 by reading the per-session `ReminderChoice` override over the account `ReminderDefault`.
- Phase 7 owns the **transport and preference surfaces**: Web Push delivery and its send-log, the notification center and unread state, the account-level `ReminderDefault` preference UI, and the per-session mute UI. Phase 7's "reminder delivery job" is the push-transport leg riding on the Phase 4 in-app row.
- Phase 4 therefore adds materializer-level and job-level evidence to the existing D-082/D-090/D-113 rows; it does not take ownership of those rows away from Phase 1 (domain) or Phase 7 (preference UI).

**Localization and accessibility boundary.** D-060 is owned by Phases 1/2/3/8, D-146 by Phases 2/3/8, and D-139 by Phases 3/8 (`TRACEABILITY.md:87`, `TRACEABILITY.md:173`, `TRACEABILITY.md:166`). Phase 4 claims none of the three. It ships its own three locales and WCAG 2.2 AA keyboard/screen-reader behavior for every Phase 4 screen (`ARCHITECTURE.md:78`, `ARCHITECTURE.md:73`) and appends its screens to the existing D-060/D-139/D-146 evidence rows. The full cross-browser matrix (D-138) and the full-site WCAG audit remain Phase 8.

Steam selection is a boundary, not a dependency: the request accepts either a Steam catalog reference or free-text game; the UI must always offer free text. PlayStation, Xbox, and N/A accept only free text (D-040/D-041/D-058/D-176; `PRODUCT_SPEC.md:254-267`, `PRODUCT_SPEC.md:668`). No Steam catalog retrieval, sync, credential, cache, or background job is part of this phase.

### 1.3 Exit criteria

Phase 4 exits only when all slices in section 12 have their named gates, one generated OpenAPI schema, and D-numbered traceability entries; every invariant command follows the lock protocol in section 6 under the per-table lock orders A-068 declares and the cross-table sequence of `P4-LK-01`, with every order imposed in SQL; no read infers session status from time; guest token paths are absent from application and Caddy logs; both attachment-first and block-first races pass for invite and join/approval; a reminder is proven to be *delivered* (not merely canceled) inside its delivery window; and browser interaction proves registered and guest flows in `en`, `pt-BR`, and `es`.

## 2. Verified current state and reconciled gaps

The pure Session aggregate, guest-link token generation, visibility/masking, recipient computation, reminder planning, and time transitions already exist. `GuestLink` uses 32 CSPRNG bytes, SHA-256 at rest, fixed-time comparison, and no capacity reservation (`src/PartyUp.Domain/Sessions/GuestLink.cs:10-14`, `:18-20`, `:73-92`). The ratified model defines the aggregate, response states, visibility, state-machine transitions, and deletion ordering (`DOMAIN_MODEL.md:63-136`, `:177-189`, `:202-249`). Those rules are not redesigned here.

There is no Session `DbSet` or configuration in the current context (`src/PartyUp.Infrastructure/Persistence/AppDbContext.cs:18-36`, `:82-84`), no session endpoint group is mapped (`src/PartyUp.Api/Program.cs:257-270`), and Hangfire is absent from every csproj and from `Directory.Packages.props`. Phase 3 deliberately binds `EmptyBlockEffectScopeProvider` and a throwing `NoSessionReminderScheduleWriter` (`src/PartyUp.Infrastructure/DependencyInjection.cs:66-67`). Phase 4 **deletes** both types in the slice that supplies real persistence rather than rewriting them in place, and updates the one test that constructs the throwing writer directly (`tests/PartyUp.Api.IntegrationTests/Friends/FriendBlockConcurrencyTests.cs:140`).

Facts the design is bound to, each read at the baseline:

- **Row locking is ordered in SQL, not in C#.** `FriendPairLocker` issues `SELECT 1 FROM users WHERE id IN (…) ORDER BY id FOR UPDATE` (`src/PartyUp.Infrastructure/Persistence/Repositories/FriendPairLocker.cs:20-27`) — Postgres `uuid` ordering. `Friendship.CanonicalPair` uses `Guid.CompareTo` (`src/PartyUp.Domain/Friendships/Friendship.cs:50`), which is a *storage key* choice (which id is `lo`), not a lock order, and is untouched by this phase. See A-068.
- **`UnitOfWork.ExecuteAsync` has no retry.** It opens one transaction, translates exactly one unique-violation constraint, and otherwise rolls back and clears the change tracker (`src/PartyUp.Infrastructure/Persistence/Repositories/UnitOfWork.cs:22-45`). A serialization failure or deadlock is currently an unhandled 500. See A-069.
- **The rate limiter is one chained global limiter, not a set of named policies.** `RateLimitPolicies.Dimensions` is a list of `RateLimitDimension(Name, PermitLimit, Window, PartitionKind, OperationIds, CoversEveryApiOperation)` composed by `PartitionedRateLimiter.CreateChained`; partition kinds are `{Ip, Email, User}`; there is no `RequireRateLimiting` named policy anywhere (`src/PartyUp.Api/Security/RateLimitPolicies.cs:15-19`, `:56-175`). The limiter is branch-scoped to `/api/v1` (`src/PartyUp.Api/Program.cs:245-247`), so any route outside that prefix is currently unmetered. See A-073.
- **`ApiOperationIds.GetSession` is taken** by `GET /api/v1/auth/session` (`src/PartyUp.Api/ApiRoutes.cs:11`) and asserted by existing tests. See A-071's inventory rule and section 8.
- **`SessionEndpointTests` already exists** as an auth/provider test class (`tests/PartyUp.Api.IntegrationTests/SessionEndpointTests.cs:8`). Phase 4's HTTP class is named `GameSessionEndpointTests`.
- **There is no `tests/PartyUp.BrowserTests` project**, no Playwright package version, and no solution entry (`PartyUp.sln` lists Domain, Application, Infrastructure, Api, Domain.Tests, Application.Tests, Api.IntegrationTests only). S6 creates it; `ARCHITECTURE.md:73` permits the Playwright lane "no later than Phase 5".
- **There is no `web/src/components/AppNavigation.tsx`.** Navigation is inline in `web/src/App.tsx:57-93` and asserted by `web/src/App.test.tsx`. S5 edits those two files.
- **`src/PartyUp.Api/Security/AntiforgeryFilter.cs` is dead code** — the live filter is `ProblemAntiforgeryFilter` in `src/PartyUp.Api/ErrorHandling/FriendGraphProblems.cs:112`, wired at `Program.cs:258`. S4 deletes the dead file.
- **The request-path sanitizer covers four friend families only** (`src/PartyUp.Api/Logging/FriendPathLogSanitizer.cs:7-13`) and `deploy/Caddyfile:30-42` carries a commented example that redacts `guest/`, not `/g/`. Both are Phase 4 gaps.

The reconciliation is therefore: Phase 1 owns session behavior and D-numbered unit rules, Phase 3 owns the stable block/deletion seam, and Phase 4 owns the relational loading, real scope providers, transactionality, jobs, HTTP/API contract, guest security, session projections, and UI. This matches the traceability split that leaves session attachment races and masked session rendering to Phase 4 (`TRACEABILITY.md:234-242`, `TRACEABILITY.md:304-308`).

## 3. Binding interpretation rulings and consolidated decision record

No new product behavior is introduced. The following implementation decisions are binding and are appended to `ARCHITECTURE.md` by the named owners in sections 12 and 13. The four `P4-*` records are named gates: a slice may not close while its gate is unproven.

| Record | Ruling | Basis |
|---|---|---|
| A-064 | **Web transport-entry exception, not a REST resource:** `GET /g/{token}` validates only, issues a protected cookie, sends `Referrer-Policy: no-referrer`, and redirects to a tokenless SPA route. It makes no database write, claim, RSVP, link consumption, or capacity reservation. It is outside the REST/OpenAPI resource surface because its sole input is a bearer URL and its sole result is an HTTP redirect/cookie exchange; every resource read/mutation remains under `/api/v1`. It carries endpoint-name metadata (`ExchangeGuestLink`) so the rate limiter can key it, and `ExcludeFromDescription()` so it is absent from `/openapi/v1.json`. | A-015; the plan's Phase 4 guest security package (`IMPLEMENTATION_PLAN.md:92`); `ARCHITECTURE.md:53`. |
| A-065 | **Guest credentials are stateless; `guest_links.state` is the single revocation authority.** The cookie is an ASP.NET Data Protection payload of `{GuestLinkId, Mode, IssuedAt, ExpiresAt}` where `Mode` is `active` or `terminal`. There is **no** credential-version column on `guest_links` and no session-level counterpart: because a link never returns to `Active` and the session's computed end is re-read on every request, the link's own `state` (plus that end) already answers every question a version counter could, and a column whose only reachable values are "before revocation" and "after revocation" is a second, driftable copy of `state`. Revocation is therefore instantaneous and server-authoritative on the next request without any cookie rewrite. Cookie name and Path include the link id, so each link has an independent credential. `Mode` gates **mutations only**; see A-074 for the terminal-view rule. | `DOMAIN_MODEL.md:99-105`; the non-mutating-GET and multiple-link requirements. |
| A-066 | `session_reminder_handoffs` is the durable source of truth. Hangfire runs recurring discovery/execution only after the transaction commits; it is never claimed to enlist atomically with EF. A locked due-row transaction revalidates and creates at most one notification. | A-016; `ARCHITECTURE.md:14`, `ARCHITECTURE.md:58`; `DOMAIN_MODEL.md:204-208`. |
| A-067 | All session commands and jobs use one application transition/materialization path. The Session's stored status is authoritative, and list/read predicates use it rather than timestamp-derived status. | `ARCHITECTURE.md:14`, `ARCHITECTURE.md:55`; `DOMAIN_MODEL.md:11-16`. |
| A-068 | **One database-imposed lock order per table, declared here; never a caller-computed order.** Every multi-row lock is acquired by a single `SELECT … FOR NO KEY UPDATE` statement carrying the `ORDER BY` declared for that table, so Postgres imposes the order. The complete declared list for Phase 4 is: `users` → `ORDER BY id`; `sessions` → `ORDER BY id`; `session_reminder_handoffs` → `ORDER BY due_at, id` (always within one already-locked session parent, §7.2); `friendships` → `ORDER BY user_lo_id, user_hi_id, id`; `blocks` → `ORDER BY LEAST(blocker_id, blocked_id), GREATEST(blocker_id, blocked_id), blocker_id, blocked_id, id` — the last two matching `P3-LK-01` (`DOMAIN_MODEL.md:16`). Any table not on this list is locked `ORDER BY id`, and adding a table to a Phase 4 lock path requires adding its key here. Across tables the sequence is the `P4-LK-01` order of §6.1. All `uuid` columns above sort in Postgres `uuid` order. No caller sorts identifiers in C# to decide lock order. Where a C#-side total order is unavoidable (diagnostics, assertions), it must be `Guid.ToByteArray(bigEndian: true)` compared with `SequenceCompareTo`, which reproduces Postgres `uuid` ordering; `Guid.CompareTo` and little-endian `ToByteArray()` are forbidden as lock orders because they disagree with it. `Friendship.CanonicalPair` remains a storage-key rule and is not a lock order. This ruling binds `P4-LK-01`, deletion (§6.2), block effects (§5.3), bulk invite/approval, and both jobs (§7.2). | The shipped `FriendPairLocker` SQL order; `DOMAIN_MODEL.md:293-295` (`P3-LK-01`); A-054. |
| A-069 | **Lock strength and bounded serialization retry.** Session and user row locks taken by Phase 4 paths use `FOR NO KEY UPDATE`. It still conflicts with `FOR UPDATE` and with itself (so mutual exclusion against the existing friend/deletion paths is preserved), but it does **not** conflict with the `FOR KEY SHARE` an FK-referencing insert takes — so writing a `notifications` or `session_participations` row never blocks behind a Phase 4 user lock. Because the friend path still takes `FOR UPDATE` on `users`, a residual deadlock class remains; therefore `IUnitOfWork.ExecuteAsync` gains a bounded retry: on `40001` (serialization failure) or `40P01` (deadlock detected) it rolls back, clears the change tracker, waits a jittered backoff (20/50/100 ms), and re-runs the work delegate in a **fresh** transaction, at most 3 attempts. The retry predicate matches SQL state `40001`/`40P01` both as `DbUpdateException.InnerException is PostgresException` (EF `SaveChanges`) **and** as a bare `PostgresException` — the raw lock and `ON CONFLICT` SQL of §6.1/§7.2 throws the latter, which the shipped translator at `src/PartyUp.Infrastructure/Persistence/Repositories/UnitOfWork.cs:29-34` does not see. Three constraints make the delegate re-runnable, and they are contract, not advice: **all entity reads occur inside the delegate** (rollback calls `ChangeTracker.Clear()`, which detaches anything the caller materialized earlier, so an entity loaded before `ExecuteAsync` must never be mutated within it); the delegate may not mutate state outside the `AppDbContext`; and any generated identifier or CSPRNG token must be produced inside it. A **nested** call — one made while `context.Database.CurrentTransaction is not null` (`UnitOfWork.cs:15-18`) — runs the delegate directly with no transaction and therefore **no retry**; the outermost `ExecuteAsync` is the only retry boundary, and §6.2's deletion retry is deliberately outside it. Exhaustion surfaces to HTTP as `503` with code `transient_conflict` and `Retry-After: 1`; to a background job it surfaces as a failed tick that the next cadence retries. | `ARCHITECTURE.md:55`; A-053; A-016. |
| A-070 | **Explicit clear list, not nullable tri-state.** `PATCH /sessions/{id}` cannot express "set to unlimited/absent" with `null`, because a JSON `null` is indistinguishable from an omitted field in a generated client. The request therefore carries only the fields being changed plus `clear: string[]`, a closed enum whose members are exactly `maxCapacity`, `notes`, and `game`. A `null` value for any body field is rejected with `400 session_validation`; a field named in `clear` and also present in the body is rejected the same way. The enum is declared in OpenAPI, so the generated client and any future mobile client see the same closed set. | `ARCHITECTURE.md:60` (OpenAPI is the mobile contract); D-091/D-121 make "clear the maximum" a first-class command. |
| A-071 | **Opaque `version` token, compared not decoded; `ifMatch` travels in the body.** `SessionDetail.version` is `base64url(HMAC-SHA256(key, sessionId ‖ xmin)[0..15])` under a dedicated Data Protection purpose. The server never decodes it: it recomputes the HMAC from the freshly locked row's `xmin` and compares in fixed time. This keeps the global transaction-id rate unobservable, which a raw base64 `xmin` would leak. `ifMatch` is a required body field rather than an `If-Match` header because the mobile-contract surface stays uniform (one JSON body, one generated operation) and because emitting `ETag` on every read would commit the whole API to conditional-request semantics it does not otherwise use; the residual cost is that RFC 9110 tooling sees no ETag, which is accepted. All Phase 4 operation ids are constants in `ApiOperationIds` and must be globally unique — `GetSession` is already taken by `/api/v1/auth/session`, so the session read is `GetSessionDetail`. | `ARCHITECTURE.md:55` (xmin optimistic concurrency), `ARCHITECTURE.md:60`; `src/PartyUp.Api/ApiRoutes.cs:11`. |
| A-072 | **One pagination shape.** Every Phase 4 list returns `{ items: T[], nextCursor: string | null }`. `nextCursor` is an opaque base64url of `{sortKey, id}`, where `sortKey` is the instant of the list's declared sort column — one per list, fixed here: `GET /sessions?scope=upcoming` and `?scope=history` sort on `sessions.start_time`; `GET /sessions/{id}/join-requests` sorts on `join_requests.created_at`. Paging is keyset: `upcoming` orders `(start_time, id)` ascending with `WHERE (start_time, id) > (@k, @i)`; `history` orders `(start_time, id)` descending with the mirrored predicate; join requests order `(created_at, id)` ascending with `WHERE (created_at, id) > (@k, @i)`. A cursor is only ever decoded by the list that issued it — a cursor presented to a different list is a `400 invalid_cursor`. Page size is fixed at 20 and is not client-controllable. A malformed or non-decodable cursor returns `400 invalid_cursor`. Offset paging is forbidden — the sweeper mutates status underneath a paging client. | `ARCHITECTURE.md:60`; A-067. |
| A-073 | **Rate limiting is dimensions, not named policies.** Phase 4 adds `RateLimitDimension` entries to the existing chained global limiter — `session-write` (30/user/minute), `session-attach` (60/user/minute, sized for a legitimate organizer approval/promotion burst), `guest-link-exchange` (20/IP/minute), and `guest-write` (20/link/minute) — plus one new `RateLimitPartitionKind.GuestLink`. Partitioning happens in the static `RateLimitPolicies.PartitionFor` (`src/PartyUp.Api/Security/RateLimitPolicies.cs:274-295`), which has no DI and runs before `UseAuthorization` (`src/PartyUp.Api/Program.cs:242-248`), so it cannot decrypt or validate a cookie. Its raw key is therefore the `{guestLinkId}` **route value** — available because the limiter branch sits after `UseRouting` — normalized to lowercase `N` form and then salted through the existing `HashPartitionKey(dimension, rawKey, pepper)` like every other dimension. When the route value is absent or unparseable the kind falls back to the caller's IP string under the same dimension name, so an attacker cannot buy exemption (the shipped `User` kind returns *no limiter* when anonymous, which is why the fallback is mandatory). Keying on the route value rather than on a validated credential means an unauthenticated caller can consume another link's bucket; that is accepted because the route value is what an attacker would have to guess anyway (a Guid v7 link id), the `default` 300/IP/minute ceiling still bounds them, and the alternative — credential validation inside a static partition function — is not reachable in this pipeline. `Program.cs`'s limiter branch predicate is extended from `StartsWithSegments(ApiRoutes.V1)` to also match `/g`, so the exchange route is covered by both its own dimension and the `default` 300/IP/minute ceiling. No `RequireRateLimiting` named policy is introduced. | `src/PartyUp.Api/Security/RateLimitPolicies.cs:15-19`, `:56-175`, `:265-280`; `src/PartyUp.Api/Program.cs:245-247`; A-059; D-150. |
| A-074 | **A credential outliving its link's Active state is not automatically a 404 — the link row's `state` decides.** A protected credential that is well-formed, unexpired, and link-id-matched is resolved against the freshly read `guest_links.state` and the session's computed end: (a) `mode=active` credential + `Active` link + session not ended → normal guest access; (b) `mode=active` credential + terminal link (`RevokedByCancel`, `RevokedByRemoval`) or ended session → `GetGuestSession` returns the terminal notice and the response re-issues a `mode=terminal` credential with a 10-minute lifetime, while every mutation returns `409 guest_link_terminal`; (c) `mode=terminal` credential + `Active` link + session not ended → 404, fail closed. The combination is forged-or-stale whenever the link is terminal or the session has ended; it also arises legitimately when a terminal credential was issued for an ended session on a still-Active link and the organizer then reschedules the start into the future within the 10-minute terminal window — there the 404 is the accepted fail-closed outcome and the guest re-opens the original link (the §9.1 reschedule-reopen residual covers it); (d) `mode=terminal` credential + terminal link/ended session → terminal notice, mutations `409 guest_link_terminal`. `EndTime` is always computed from immutable start plus duration and is never a stored domain column (`DOMAIN_MODEL.md:13-15`), and Phase 4 adds no `end_time` column to work around that. **Nor is there an expression index over the computed end:** `timestamptz + interval` is STABLE, not IMMUTABLE — its result depends on `TimeZone` — so `CREATE INDEX` rejects any expression containing it, regardless of `make_interval` itself being immutable.

The sweep instead drives off the ordinary composite index `(status, start_time, id)` and bounds its scan with the duration cap. A candidate row must satisfy

```
status IN (<Unconfirmed>, <Confirmed>)
AND start_time <= now()
AND start_time >= now() - interval '1440 minutes'
AND start_time + make_interval(mins => duration_minutes) <= now()
```

The first three predicates are index-driven and select a bounded window; the fourth is the exact due test, applied as a filter over that window. The bound is **complete, not heuristic**: `duration_minutes` is checked to 15..1440 in this same table, so any session whose end is at or before `now()` has a start at or after `now() - 1440 minutes`. Raising the duration cap requires raising this interval in the same commit. The sweep query is raw SQL, keyset-paged on `(start_time, id)` — no EF-translated arithmetic and no offset paging. The index bounds the scan, but ordered output for the `status` IN-list on the leading column is guaranteed only on PostgreSQL 17+ — older majors may insert a sort node — and paging correctness is unaffected either way because the 1440-minute window bounds the candidate set.

### 4.2 Required indexes, load shapes, and concurrency

`sessions` has `(organizer_id,status,start_time)` and `(status,start_time,id)`; the latter serves both the A-072 `upcoming`/`history` keysets and the §4.1 bounded due sweep. There is no expression index. `session_participations` has `(user_id,status,session_id)`, `(session_id,status,is_waitlisted)`, and the two partial uniqueness indexes. `join_requests` has `(session_id,status,created_at,id)` — matching the A-072 join-request keyset — and the pending partial uniqueness index. The Session repository offers two distinct load methods: a projection read that never mutates, and `LoadForUpdateAsync` that issues `FOR NO KEY UPDATE` on the session parent before loading participations, links, requests, mutes, and handoffs.

**Concurrency tokens.** Only `sessions` carries one. Npgsql maps `xmin` as a `uint` shadow property of type `xid`; it is neither an "unsigned integer" column nor addressable in LINQ except through `EF.Property<uint>(session, "xmin")`, which is how the projection mapper reads it. Child tables deliberately carry **no** token: they are only ever written under the parent's lock, and an unmapped token would surface as a `DbUpdateConcurrencyException` with no recovery path.

**Edit concurrency.** Every `SessionDetail` includes `version` per A-071. `EditSessionRequest.ifMatch` is required and must equal it. Ordering inside the edit transaction is fixed, because it determines whether routine sweeps produce spurious conflicts:

1. Pass fail-closed visibility and organizer authorization.
2. Lock the session parent (`FOR NO KEY UPDATE`) and read `xmin` — **this is the comparison point.**
3. Compare `ifMatch` against the HMAC of that `xmin`. Missing/malformed → `400 invalid_if_match`; well-formed mismatch → `409 session_conflict`. Either writes nothing and returns no current detail.
4. Apply any due transition (A-067). A status flip performed *by this transaction* cannot invalidate the caller's token, because the comparison already happened. If the transition makes the session terminal or time-locks the field, the edit returns `409 session_terminal` or `422 session_time_locked` — not a conflict.
5. Apply the edit, materialize notifications and handoff changes, and return a fresh `version`.

A background sweep that flips status **between** the client's read and their edit does bump `xmin` and therefore does produce a genuine 409. This is accepted and visible: the web client refetches the detail and retries the edit once automatically, surfacing `errors.codes.session_conflict` only if the second attempt also conflicts. `xid` wraparound could in principle alias two `xmin` values, but that requires ~2^32 transactions between the client's read and their edit, and the parent lock plus step 4's revalidation bounds the consequence to a stale-but-legal edit; it is a documented residual, not a mitigated risk.

This optimistic check never replaces parent locking. Any command touching capacity, response, waitlist, confirmation, guest claim/response/removal, block scope, deletion scope, start, min, or max follows section 6 and locks the parent before child/occupancy work.

### 4.3 Migration and round-trip gates

S1 owns one migration and snapshot that creates every table, check, FK (`RESTRICT` where history must survive; cascade only owned guest children), explicit index, partial index, and `xmin` mapping. Its real-Postgres integration tests must create a Session with registered/guest active and waitlisted participations, request, unclaimed and claimed links, mute, every non-poll link state, pending/canceled/delivered handoffs, and every game shape; save; clear the context; reload with `LoadForUpdateAsync`; and prove semantic equality of status, token digest, participants, link state, requests, handoff state, and reminder choice. A duplicate token, duplicate participant, invalid XOR reference on `guest_links`/`join_requests`/`notification_mutes` (both columns null and both non-null), invalid capacity, and a second reminder notification for one handoff must each fail at the database boundary.

That widening lands in **S2**, not S1: its sole implementer `src/PartyUp.Infrastructure/Deletion/DeletionScopeProvider.cs` is S2-exclusive, and widening the interface a slice earlier would break the S1 build. Declaring an unimplemented port is legal C#; registering one is a compile error.

Visible registered reads use the one visibility engine and fail closed with the exact same `session_not_found` 404 for nonexistent, private, blocked-organizer, removed, and unqualified inherited access. A guest link is its own proof, scoped to one link/session; its terminal response is a constrained terminal notice, not a registered visibility bypass (`DOMAIN_MODEL.md:177-189`). **Link states are the four in `DOMAIN_MODEL.md:99`.** There is no "expired" *link* state for a session: a past-`EndTime` link is still `Active` and resolves to the "session ended" notice. `ExpiredPoll` is Phase 6 only. Design text, problem codes, and locale keys use `ended`, never `expired`, when describing a session link.

### 5.2 Use cases

Phase 4 implements `CreateSession`, `EditSession`, `InviteRegisteredUsers`, `CreateGuestLinks`, `RevokeGuestLink`, `RemoveSessionGuest`, `RespondToInvitation`, `LeaveSession`, `RequestJoin`, `WithdrawJoinRequest`, `ListSessionJoinRequests`, `ApproveJoinRequest`, `RejectJoinRequest`, `PromoteWaitlistParticipant`, `RejectWaitlistParticipant`, `SetSessionReminder`, `CancelSession`, `GetSessionDetail`, `ListUpcomingSessions`, `ListCompletedHistory`, `ResolveGuestLink`, `ClaimGuest`, `RenameGuest`, `RespondAsGuest`, `GetGuestSession`, `ApplySessionBlockEffects`, `ApplySessionDeletionEffects`, and `ExecuteSessionDueTransitions`.

`ListSessionJoinRequests` applies registered visibility plus organizer authorization and returns the same `session_not_found` 404 for missing, hidden, non-organizer, or otherwise unauthorized callers. `RemoveSessionGuest` is organizer-only, identifies the claimed guest by participation id (never bearer token or link id), locks the parent before children, applies the aggregate's removal rule, revokes the link to `RevokedByRemoval` — which is by itself the credential kill switch under A-065 — re-evaluates capacity/waitlist/confirmation, cancels any applicable handoff, materializes only derived Session events, and leaves the bearer with the A-074 terminal view. `RevokeGuestLink` remains the organizer operation for an unclaimed link. `SetSessionReminder` writes the per-session `ReminderChoice` override on the caller's own registered participation, is rejected with `422 reminder_not_eligible` for a guest row, a `Removed`/`Declined` row, or a terminal session, and is a §7.1 replan trigger. Guest claim/response/rename use the same transition and parent-lock path as registered mutations. Guest last-write-wins means no client version/conflict rule, never absence of the parent lock.

**Create.** Applies defaults min 4, max 4, 2 h, N/A, non-private (`PRODUCT_SPEC.md:244-252`, D-129) and seeds organizer Going. It rejects a start outside `[now+15 min, now+1 year]` (D-130), an invalid 15-minute duration (D-142), invalid text, or non-private creation with no directly invited registered friend (D-099). Bulk inputs are bounded: `inviteeUserIds` 1..50 distinct ids, `guestLinkCount` 0..20 — an unbounded count would let one authenticated request mint 100k CSPRNG rows or take 10k row locks.

**Edit.** Organizer only. The rules are `DOMAIN_MODEL.md:121-136` verbatim, with these points made explicit because reviewers found them missing:

- Start and min close at start (D-168). A **start change is re-validated against D-130** against the current clock — the new start must itself lie in `[now+15 min, now+1 year]`; it is not merely "different from the old one".
- A start change resets every `Pending`/`Going`/`Maybe`/waitlisted **and `Declined`** row to Pending with waitlist flags cleared, never `Removed` rows, including the organizer's own row (D-063). **Reschedule notification recipients are computed after that reset**, so revived invitees are told; computing them from the pre-reset roster would silently drop exactly the people the reset just re-invited.
- Max cannot undercut active Going+Maybe occupancy or min (D-121/D-141); clearing to unlimited is rejected while the waitlist is non-empty (D-091, §12-1). Clearing is expressed through A-070's `clear` list.
- Only start/duration/min produce notifications; title, game, platform, notes, max, and privacy are silent (D-122/D-123).

**In-progress carve-out (D-089).** `session_responses_closed` is not a blanket post-start rejection. After start and before `EndTime`, an **active or waitlisted `Going`↔`Maybe` flip is still accepted** (`DOMAIN_MODEL.md:126`); what closes at start is a `Pending` or `Declined` row moving to an attendance state, and leaving (D-055 leave is before-start only — post-start the only waitlist exit is the organizer's reject). A started `Confirmed` session can never unconfirm (D-106). Join requests stay open until `EndTime` (D-173).

**Cancellation (D-156/D-157).** `Unconfirmed`, `Confirmed`, in-progress, and **`Completed`** sessions all cancel; `Expired` does not — the §5.5 state-machine Cancel row admits only `Unconfirmed`/`Confirmed`/`Completed` (`DOMAIN_MODEL.md:115`) — and an already-`Canceled` session is a no-op. Due transitions are applied before the guard, so a logically expired session cannot be canceled and a logically completed one cancels as Completed. Cancellation revokes every guest link (D-174), lapses pending join requests, and notifies the access-scoped audience minus the organizer (D-166).

### 5.3 One transaction per state mutation

Every command executes `IUnitOfWork.ExecuteAsync` once, under the A-069 retry contract. Within it: acquire locks in A-068 order; load the full aggregate; apply due transitions first; authorize and apply the domain command; re-evaluate confirmation where required; collect domain events; compute recipients and write notification rows; write reminder-handoff changes; persist all rows. Any notification/handoff/database failure rolls back the aggregate mutation. Guest and registered notification recipients are never mixed: guests receive no rows and no transport work (D-167).

Because the delegate can be re-run by A-069, guest-link tokens, handoff ids, and Guid v7 keys are generated **inside** the delegate; nothing outside `AppDbContext` is mutated within it.

**Block effects** replace the Phase 3 empty scope. The provider discovers every affected non-terminal, not-ended organizer/counterpart session and relevant open request, then locks the affected session parents **in one A-068-ordered statement** — a concurrent pair of blocks sharing two sessions must not be able to take them in opposite orders. It then calls the existing executor once, marks required participations Removed, lapses requests, re-evaluates confirmation, cancels handoffs, and materializes only derived Session events.

**Deletion scope** runs the ratified ordering (`DOMAIN_MODEL.md:239-249`): cancel future owned sessions; remove the subject from other not-started sessions; **lapse the subject's own open join requests** (`DOMAIN_MODEL.md:243` — this is part of step 3 and was previously unstated here); retain in-progress and Completed participation/history; cancel reminder handoffs; then tombstone in the established executor.

## 6. Lock algorithm, races, visibility, masking, and notification materialization

### 6.1 `P4-LK-01` algorithm

1. Resolve actor/resource authorization without locking arbitrary target ids; hidden/missing ends as 404.
2. Build the complete affected registered-user set: actor, organizer, counterpart/invitee/requester/participant, and deletion subject where applicable. Lock those `users` rows with **one** statement, `… WHERE id = ANY(@ids) ORDER BY id FOR NO KEY UPDATE` (A-068/A-069).
3. Lock relevant friendship rows `ORDER BY user_lo_id, user_hi_id, id` and both block directions `ORDER BY LEAST(blocker_id, blocked_id), GREATEST(blocker_id, blocked_id), blocker_id, blocked_id, id` — the A-068 declared keys for those tables, ordered by the database, in one statement per table.
4. Lock the session parent(s) with `… ORDER BY id FOR NO KEY UPDATE`; then load all participations, guest links, join requests, mutes, and applicable handoffs. No occupancy query occurs earlier.
5. Re-evaluate friendship, block, lifecycle, visibility, terminal/time gate, and duplicate eligibility after locks. Mutate only if still valid.
6. Persist aggregate, notifications, and handoff changes before commit.

Invite, join request, approval, re-invite of Declined, and any restored attachment use all six steps. RSVP/promotion/reject/guest responses that introduce no new registered counterpart still lock the session parent before occupancy. **Bulk invite and bulk approval lock the union of users and graph rows in one A-068-ordered statement, never in request-input order.**

The mandatory race gates are exact. In attachment-first tests, invite or join/approval holds graph locks, commits the attachment, then block observes it and removes/lapses it; the final result contains the block and no active counterpart attachment or reminder. In block-first tests, block commits first, attachment waits, rechecks block under the same locks, returns an indistinguishable 404, and writes no participation/request/reminder/notification. Each ordering is tested for direct invite and for join/approval, with a parent-lock assertion before every occupancy read.

### 6.2 Deletion pre-lock/reload protocol

`ExecuteDeletionForUserUseCase` must not lock the deletion subject and subsequently acquire a lower-ordered counterpart. Inside its transaction it first asks `IDeletionScopeProvider.DiscoverAffectedUserIdsAsync` for the complete candidate set **without locks**: the subject; all registered organizers, participants, and pending requesters on sessions that deletion can cancel or change; and all friendship/block counterparts. It deduplicates the set and locks every corresponding `users` row in one A-068-ordered statement before it loads any mutable deletion scope, friendship, block, session parent, handoff, participation, or request row.

After those user locks, `IDeletionScopeProvider.LoadForUpdateAsync` reloads the complete scope using the normal graph order and locks affected session parents in one A-068-ordered statement before their handoffs and children. It recomputes the candidate user set from the locked scope. If it differs from the discovered set, the transaction performs no writes and aborts.

**The retry is outer and bounded.** A changed candidate set cannot be retried inside the running `ExecuteAsync` — the transaction is already poisoned and the change tracker is cleared on rollback. The use case therefore raises a `DeletionScopeChangedException`, and the caller loops: at most 3 attempts, each a fresh `ExecuteAsync` with a jittered 20/50/100 ms backoff, re-running discovery from scratch. Exhaustion abandons this user for this tick; the existing Phase 2 grace-expiry hosted service retries on its next cadence, so no user is lost and no unbounded loop exists. Only an unchanged set may run `DeletionExecutor.Execute`, `DeletionResultApplier.ApplyAsync`, credential purge, transactional journal append, notification/handoff materialization, and tombstone. The deletion tests must force a changed-set retry and prove no first-attempt write, canonical user locking, bounded attempts, and the D-092 future-only outcomes including the subject's own lapsed join requests.

### 6.3 Notification contract

`ISessionNotificationMaterializer` accepts structured Session events only. It uses the recipient matrix in `DOMAIN_MODEL.md:218-231`: invitation → new invitee; confirmation/unconfirmation/reschedule → registered pending/Going/Maybe/waitlisted participants plus organizer; cancellation → registered direct-access participants minus organizer; join received/vacancy → organizer; accepted/rejected → requester; waitlist added/promoted/rejected → subject. Reschedule recipients are computed **after** the D-063 reset (§5.2). Mutes suppress every non-reminder record at write time (D-090/D-113). Cancellation is access-scoped; derived rows are not allowed to reveal a block action, block direction, or actor. The renderer applies recipient locale and identity masking at read time, so a later block or tombstone masks historical notification identities.

No notification is written for title, game, platform, notes, max, or privacy edits. Duration and start emit reschedule; min and capacity/roster changes emit only the specific domain events. Job and request paths call the same materializer, ensuring exact recipient semantics.

## 7. Durable reminders and scheduled work

### 7.1 Reminder handoff contract

For every eligible registered Going/Maybe participant, including waitlisted (`DOMAIN_MODEL.md:208`, §12-30), the writer computes `due_at = start_time - effective choice`, where the per-session override takes precedence over the account default (D-082). It writes or updates one handoff in the mutation transaction. `Off`, `Removed`, `Declined`, a terminal session, or a non-future due instant produce Canceled/no handoff. Replan increments `version`; cancellation increments it and sets state `Canceled`.

Replan/cancel is invoked after RSVP, leave, approval, promotion/rejection, **`SetSessionReminder`**, start or duration change, cancellation, block removal, and deletion removal. The durable row, not a Hangfire enqueue, is the crash boundary. EF commits session state, notification rows, and handoff state together; a rollback leaves none.

**Delivered handoffs and reschedules — open interpretation, resolved by ruling and flagged for ratification.** A blanket "a delivered reminder is never recreated" makes the recompute trigger a permanent no-op: reschedule a session two weeks out after its reminder already fired and the participant never gets another one. `DOMAIN_MODEL.md:208` gives the recompute triggers but does not say what a *delivered* handoff does when its due instant moves forward, so this design does not invent product behavior. **S2 must add a `DOMAIN_MODEL.md` §12 interpretation note resolving it, and this design's recommended resolution — the one the code is written against unless the note rules otherwise — is:** when a start-time or duration change recomputes `due_at` to an instant strictly in the future, a `Delivered` handoff resets to `Pending`, clears `delivered_at`, and increments `version`; a `Delivered` handoff whose recomputed instant is still in the past stays `Delivered`. The `(session_id,recipient_user_id)` uniqueness still guarantees one live reminder per user per session, and the `ux_notifications_session_reminder_once` index is keyed on `reminder_handoff_id`, so a reset row legitimately produces a second notification for a genuinely different session time.

### 7.2 Hangfire topology

`P4-REMIND-01` adds Hangfire and Hangfire.PostgreSql to `Directory.Packages.props`, a `PackageReference` to **both** `PartyUp.Infrastructure.csproj` (job types) and `PartyUp.Api.csproj` (server + storage registration in the composition root), and registers the server with the dashboard disabled. **Hangfire.PostgreSql creates and owns its own schema at server start**, outside EF: S3 pins it to a dedicated schema named `hangfire`, and that schema is explicitly excluded from the EF migration, from `AppDbContextModelSnapshot.cs`, and from the §4.3 round-trip gate. No EF migration ever references a `hangfire.*` object.

Two recurring jobs run at one-minute cadence; both carry `[DisableConcurrentExecution(timeoutSeconds: 55)]`. That attribute **blocks for 55 s and then throws**, so an overlapping tick surfaces as a failed Hangfire job rather than a silent skip; that failed job is the intended overlap signal and the next cadence retries the work unchanged (both jobs are idempotent). S3's gate asserts the failure is observable and that no work is duplicated, so steady overlap noise is a monitoring signal that the tick budget is exceeded, not an error to suppress.

- **`SessionDueSweepJob`** pages candidates from `sessions` using the §4.1 bounded predicate — materialized status `Confirmed`/`Unconfirmed`, `start_time` inside `[now() - 1440 minutes, now()]` off the `(status, start_time, id)` index, and the exact `start_time + make_interval(mins => duration_minutes) <= now()` filter — with keyset paging on `(start_time, id)`. The index bounds the scan; the planner may add a sort node for the status IN-list on pre-17 PostgreSQL majors, and paging correctness is unaffected because the 1440-minute window bounds the candidate set. It processes at most 500 sessions per tick. **Each candidate gets its own transaction**: lock the parent, apply the shared due transition, materialize resulting rows, commit. A wide multi-session transaction is forbidden — it would hold parent locks across the whole minute's batch and block every interactive RSVP on those sessions.
- **`SessionReminderDueJob`** performs an unlocked discovery query for due handoff candidate ids and their `session_id`s (`state = 'Pending' AND due_at <= now`), bounded to 500 candidates per tick and keyset-paged; it locks and loads nothing during discovery. It groups candidates by `session_id` and then **opens one transaction per session**, not one per tick. Inside that transaction it locks the session parent (`FOR NO KEY UPDATE`), then that session's handoff rows in `(due_at,id)` order, then participations and other children. It may never lock a handoff before its parent. Because each transaction touches exactly one session parent, no cross-session parent-lock ordering exists to get wrong; the handoff rows within it are ordered by the database.

**Delivery window.** Discovery finds only past-due rows, so "past due ⇒ cancel" would deliver nothing, ever. Under the lock, the job:

- **delivers** when `now < start_time`, the session status is non-terminal, the participation is still an eligible Going/Maybe registered row, and the handoff's `version`/`state` are unchanged since discovery;
- **cancels** (state `Canceled`, no notification) when `now >= start_time`, the session is terminal, or the participant is no longer eligible — this is the `DOMAIN_MODEL.md:208` "already past is skipped, never fired late" rule applied to the *session start*, which is the instant the reminder was about;
- **increments `attempts` and records `last_attempt_at`** on every execution attempt, moving the row to `Failed` at 5 attempts.

**Duplicate suppression uses the database, not an exception path.** The reminder notification is written with `INSERT INTO notifications (…) … ON CONFLICT (reminder_handoff_id) WHERE type = <SessionReminder> DO NOTHING` — the partial-index inference form — issued as raw SQL by the handoff store. The handoff is then marked `Delivered` in the same transaction regardless of rows affected. There is no "catch the unique violation and reload" path: a unique violation aborts the Postgres transaction (`25P02`), after which no reload can run and `UnitOfWork` has already rolled back and cleared the tracker. No savepoint API is introduced.

Jobs are at-least-once. A retry after commit finds terminal status or `Delivered` and no-ops. A failure before commit rolls back both the notification and the `Delivered` mark. No job invokes external push; that remains Phase 7.

The Phase 2 deletion hosted service remains responsible for identifying grace expiry. Its established `ExecuteDeletionForUserUseCase` calls the extended session deletion scope inside its existing transaction and its §6.2 outer retry; it is not replaced by Hangfire. Hangfire begins with session sweep and reminder discovery only.

### 8.1 Guest exchange and guest API

`GET /g/{token}` is the A-064 transport exception outside `/api/v1`. An unknown, malformed, or non-resolvable token returns **302 to `/guest/invalid` with no cookie** rather than a problem body. ## 9. Guest-security package

### 9.1 Credential, cookie, and redirect

The exchange hashes the presented token, resolves the `guest_links` unique digest with fixed-time comparison, and protects `{guestLinkId, mode, issuedAt, expiresAt}` with a dedicated Data Protection purpose (A-065 — no version field). Cookie name is `pu.g.{guestLinkId:N}`, Path is `/api/v1/guest/{guestLinkId}`, `HttpOnly=true`, `Secure=true` outside development, `SameSite=Lax`, and `Max-Age` is the smaller of 400 days and the remaining link/session lifetime. The redirect route `/guest/{guestLinkId}` contains no bearer material and reads only its path-scoped cookie API. Multiple links coexist: each has a separate cookie name, path, and payload, and each is revoked independently through its own `guest_links.state`.

The resolver verifies payload purpose, link-id equality, expiry, `mode`, the freshly read `guest_links.state`, and session end on every guest API request, resolving the four A-074 branches. No guest GET creates a guest identity, participation, credential row, RSVP, reservation, notification, or reminder.

For a resolvable revoked, canceled, or ended link, the exchange overrides the active-lifetime rule: it protects a `mode=terminal` credential whose protected expiry and cookie `Max-Age` are a bounded **10 minutes** from exchange, independent of remaining link/session lifetime. The terminal validator permits only `GetGuestSession` and rejects claim, rename, and response with `409 guest_link_terminal`. An active credential continues to require an Active link and a not-ended session. A zero or negative remaining active lifetime therefore cannot delete the cookie before tokenless terminal rendering.

Three residuals are documented rather than mitigated away:

- **The token survives in browser history.** The exchange is a 302, so the `/g/{token}` URL stays in the visitor's history and in any shared-device profile. D-048 forbids renewal, so rotation is not available; the compensating controls are non-renewability, organizer revocation (D-150), and the fact that possession is *defined* to control the guest identity (D-115).
- **A later reschedule can outlive the cookie.** `Max-Age` is fixed at issue from the then-current session end; moving the start later can leave the cookie expiring first. The tokenless route then returns 404 and the SPA renders `guest.linkExpiredReopen`, telling the bearer to open their original invitation link again — which still works, because the link itself was never renewed or rotated.
- **Guest cookies accumulate** toward the ~180-cookie-per-domain browser cap and could in principle evict `pu.auth`. Each exchange therefore emits `Set-Cookie … Max-Age=0` for every `pu.g.*` cookie present on the request whose payload is expired or whose 10-minute terminal window has closed, bounding accumulation to links the visitor is actively using.

### 9.2 Logging, headers, and abuse controls

The global response policy and the exchange route set `Referrer-Policy: no-referrer`; guest HTML also carries `<meta name="referrer" content="no-referrer">`. Caddy rewrites the access-log URI before emission so `/g/<anything>` becomes `/g/REDACTED`, including query variants — the shipped commented sample redacts `guest/` and must be corrected to `/g/` when it is uncommented — and the log format omits the `Referer` header entirely, which neither existing redaction rule covers. `FriendPathLogSanitizer` (kept under its current name so `RequestLoggingTests` and `CaddyAccessLoggingTests` stay valid) gains the `/g/` family and maps it to `/g/REDACTED`; Serilog records no headers, no `Location`, no raw token, no token hash, no protected cookie, and no request body. Redirect `Location` is only `/guest/{guid}` or `/guest/invalid`. Error messages never echo a token.

`guest-link-exchange` is source-partitioned and target-independent; malformed, unknown, active, revoked, and ended token paths consume the same lease shape (D-150). `guest-write` partitions on the salted `{guestLinkId}` route value and falls back to the IP partition when that route value is absent or unparseable (A-073) — it never inspects a cookie, because partitioning runs before authorization — so no cookie value can buy exemption. Rate-limit 429 uses the existing problem envelope and `Retry-After`. GET is `no-store`; browser previews exercise only the exchange read path. Guest access has no age gate, blocking, report flow, notification channel, graph extension, or account reconciliation.

Integration tests configure a per-factory temporary Data Protection key directory, because an ephemeral in-memory key ring re-keys on host restart and would make guest-cookie assertions flaky.
