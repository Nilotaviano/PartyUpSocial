- **Avatars on the API-blocked surfaces (Tier 2)** (owner-split 2026-08-10, after the Tier 1 client sweep shipped): the remaining surfaces cannot show an avatar without a **backend DTO change** — the response types carry no avatar field at all. Affected: `RosterEntryResponse` (session roster + waitlist), `PollRosterEntryResponse` and `PollFinalizationPreviewRosterEntryResponse` (poll voters, finalize preview), `NotificationResponse` (only `actorDisplayName`), `FriendRequestItemResponse` (username only, no display name either), `BlockedUserResponse` (username only), `SteamMatchedUserResponse` (username only), and `MaskedParticipant` (join requests, organizer display, considered friends, calendar layer owners).
  **`MaskedParticipant` is the D-076 masking type — treat it as security work, not a UI tweak.** If the server ever emits a real avatar for a masked participant, a blocked user's identity leaks through the disc, defeating the "Anonymous User" masking. Any change there needs server-side masking tests proving the avatar is withheld exactly when the display name is, and `AvatarDisc`'s `masked` prop forced on the client. Consider doing the non-masked DTOs first and `MaskedParticipant` last, or never.
  Also needs: a spec row on **where** avatars appear (currently undecided), and `gen:api` rerun after any DTO change. Reuse `AvatarDisc` (`xs`/`sm`/`md`); do not add a second avatar component.
- **Duration field has no unit** (owner, 2026-08-10): `/sessions/new` renders a bare `Duration` label over a number input whose value is **minutes** (`SessionCreatePage.tsx:408-427`, default `120`, `min`/`step` 15). Nothing on screen says minutes, so `120` reads just as easily as hours. Cheapest correct fix: put the unit in the label or a suffix next to the field and localize it in all three locales (a placeholder alone is not enough — placeholders vanish on input). Consider whether a duration this coarse deserves an hours+minutes pair instead of raw minutes; the wire contract (`durationMinutes`) stays either way. Same field appears on the poll create page — check and fix both.
- **Steam "catalog" selection is a raw App ID box** (owner, 2026-08-10): on `/sessions/new` with platform Steam, picking **Catalog** reveals a second free-text input that expects the numeric Steam **App ID** (`SessionCreatePage.tsx:489-497`), carrying only an `aria-label` and no visible label. So the owner sees two text boxes that appear to do nothing, and "catalog selection" in practice means knowing that Counter-Strike 2 is `730`.
  This is a **shipped shortfall against D-176** ("only Steam offers catalog selection, per the D-058 fallback") — there is no catalog search at any layer: no endpoint under `src/PartyUp.Api/Endpoints/` and no catalog client in Application/Infrastructure. Needs a real design pass, not a patch. Points to settle: which Steam source (the `ISteamApps/GetAppList` dump is ~200k entries and needs server-side caching plus fuzzy search; the storefront search endpoint is undocumented and unstable), whether the API key PartyUp already configures for auth/import may be reused for catalog calls under Steam's terms, cache/refresh cadence, and what happens when the catalog is unreachable (D-058's free-text fallback is the obvious answer). Until it exists, the honest interim fix is to **stop presenting an App ID box as "catalog"** — either hide the catalog radio or label the field plainly as a Steam App ID with help text.

  Library note for the design pass: PartyUp's grid is a **painting** surface (drag to declare availability), which is close to the opposite of FullCalendar's core strength (displaying events). Weigh that before adopting it — navigation and month views are where it would genuinely earn its weight, while interaction and styling are where it would likely be fought. Owner suggests evaluating the FullCalendar library (https://github.com/fullcalendar/fullcalendar — core is MIT; some plugins are paid "premium", check which features fall where before committing). Evaluate against: bundle size, i18n (pt-BR/es built-in), WCAG keyboard/SR support, and A-013 (no premature dependencies) — then a design pass before implementation.
