- **Avatars on the API-blocked surfaces (Tier 2)** (owner-split 2026-08-10, after the Tier 1 client sweep shipped): the remaining surfaces cannot show an avatar without a **backend DTO change** — the response types carry no avatar field at all. Affected: `RosterEntryResponse` (session roster + waitlist), `PollRosterEntryResponse` and `PollFinalizationPreviewRosterEntryResponse` (poll voters, finalize preview), `NotificationResponse` (only `actorDisplayName`), `FriendRequestItemResponse` (username only, no display name either), `BlockedUserResponse` (username only), `SteamMatchedUserResponse` (username only), and `MaskedParticipant` (join requests, organizer display, considered friends, calendar layer owners).
  **`MaskedParticipant` is the D-076 masking type — treat it as security work, not a UI tweak.** If the server ever emits a real avatar for a masked participant, a blocked user's identity leaks through the disc, defeating the "Anonymous User" masking. Any change there needs server-side masking tests proving the avatar is withheld exactly when the display name is, and `AvatarDisc`'s `masked` prop forced on the client. Consider doing the non-masked DTOs first and `MaskedParticipant` last, or never.
  Also needs: a spec row on **where** avatars appear (currently undecided), and `gen:api` rerun after any DTO change. Reuse `AvatarDisc` (`xs`/`sm`/`md`); do not add a second avatar component.
- **Poll organizer cannot cancel a poll from the UI** (owner, 2026-08-10; scope corrected on investigation): the reported gap was "no way for the creator to delete a session/poll". **Sessions are already complete** — `DELETE /api/v1/sessions/{id}` (`SessionEndpoints.cs:53`) is wired to an organizer-gated confirm dialog (`SessionDetailPage.tsx:397` `CancelSessionDialog`). The real gap is polls: the backend endpoint **already exists** (`POST /api/v1/polls/{pollId}/cancel`, `PollEndpoints.cs:82`, backed by `Poll.Cancel`), but no web client code calls it — `pollQueries.ts` has no cancel helper and `PollDetailPage` renders no control. So this is **client-only plumbing**: a query helper, an organizer-gated confirm dialog mirroring `CancelSessionDialog`, i18n in three locales, and tests. The term the owner was reaching for is **cancel**, not delete — cancellation is a state transition that keeps the record (and per D-174 immediately revokes the poll's guest links); nothing is hard-deleted.
- **No self-removal from a poll** (owner, 2026-08-10; scope corrected on investigation): again **sessions are already complete** — `DELETE /api/v1/sessions/{id}/my-participation` (`SessionEndpoints.cs:92`) is wired to a "Leave" button beside the RSVP controls (`SessionDetailPage.tsx:424`). Polls have **no equivalent at any layer**: no `my-participation` route in `PollEndpoints.cs`, and no use case. The domain is not the blocker — `Poll.RemoveParticipant` (`Poll.cs:460`) exists, but it is the organizer-driven removal path, so check whether self-removal is legitimately the same transition or needs its own (notification differences, whether a departed participant may rejoin, and what happens to their existing votes).
  This one is **cross-stack**: use case + endpoint + antiforgery/op-id inventories + `gen:api` + client + tests.
  **Owner ruling, 2026-08-10: a leaver's votes are withdrawn.** Needs a D-number when implemented (the spec covers a session's "departed participant" losing visibility but is silent on the poll equivalent, and D-080 does not state vote retention). Consequences to work through against that ruling:
  - Withdrawing votes changes option tallies, so the finalization preview and any "best option" arithmetic must recompute — confirm no cached/materialized tally trusts a stale count.
  - **D-172 interaction:** finalization response time is the voter's *first-response* timestamp and is explicitly unchanged by revisions. If a leaver rejoins and votes again, decide whether their first-response clock restarts or their original stands — withdrawal is not a "revision", so D-172 does not answer it.
  - Decide whether a departed participant may rejoin at all (session side has join requests; polls may differ), and whether withdrawal is silent or notifies the organizer.
  - A poll already finalized or cancelled must not be mutated by a late leave.
