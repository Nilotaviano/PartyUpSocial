- **Avatars on the API-blocked surfaces (Tier 2)** (owner-split 2026-08-10, after the Tier 1 client sweep shipped): the remaining surfaces cannot show an avatar without a **backend DTO change** — the response types carry no avatar field at all. Affected: `RosterEntryResponse` (session roster + waitlist), `PollRosterEntryResponse` and `PollFinalizationPreviewRosterEntryResponse` (poll voters, finalize preview), `NotificationResponse` (only `actorDisplayName`), `FriendRequestItemResponse` (username only, no display name either), `BlockedUserResponse` (username only), `SteamMatchedUserResponse` (username only), and `MaskedParticipant` (join requests, organizer display, considered friends, calendar layer owners).
  **`MaskedParticipant` is the D-076 masking type — treat it as security work, not a UI tweak.** If the server ever emits a real avatar for a masked participant, a blocked user's identity leaks through the disc, defeating the "Anonymous User" masking. Any change there needs server-side masking tests proving the avatar is withheld exactly when the display name is, and `AvatarDisc`'s `masked` prop forced on the client. Consider doing the non-masked DTOs first and `MaskedParticipant` last, or never.
  Also needs: a spec row on **where** avatars appear (currently undecided), and `gen:api` rerun after any DTO change. Reuse `AvatarDisc` (`xs`/`sm`/`md`); do not add a second avatar component.
