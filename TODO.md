- **Auto-confirm suggested poll options**: when a participant suggests a poll option, automatically record their vote as Available ✅ on that option (today suggesting casts no vote; suggester must vote on their own option separately). Touches the poll voting domain (D-080 family) — needs a spec decision, then Domain (`Poll.SuggestOption`) + tests.
- **FriendPairLocker robustness under concurrent load** (found by Phase 7 S6 browser lane, dispatch cadence at 2s): `AcceptFriendRequestUseCase` intermittently 500s with `OperationCanceledException` inside `FriendPairLocker.LockAsync` when the push dispatch job holds contended rows. Reproduce via the lane without its bounded retry (`PushEnableFlowTests` `BefriendWithRetryAsync`), then fix the lock acquisition (timeout/retry semantics), then drop the test retry.
- **Auth validation UX beyond password length**: `auth_validation` is one code for every auth validation message (password, email format); the client renders one localized string per code, so distinct causes aren't distinguishable in the user's language. Consider per-cause codes or localized detail if reports recur. `AccountDeletionEndpoints`/`ExternalAuthEndpoints` email-validation sites still answer the global `validation_failed`.
- **Avatars are plaintext-only and near-invisible** (owner, 2026-08-10): avatar should render as an emoji, and today it only shows on the Friends list — nowhere else in the app (rosters, notifications, settings, session/poll views). Needs a render-surface inventory + likely a spec touch on where avatars appear.
- **No logout button** (owner, 2026-08-10): the app offers no sign-out affordance. Backend session revocation exists (ban path signs out everywhere); needs the user-facing control + spec row for where it lives (settings? nav?).
- **Password validation bubble is native, unlocalized, and ugly** (owner, 2026-08-10, screenshot in session): the new-password minlength error is the browser's built-in HTML5 validation tooltip — Chrome renders it in the OS language (English on a pt-BR UI) and in default chrome styling. Replace with app-rendered, i18next-localized inline validation (suppress native bubble via `noValidate` + own checks). Also spotted on the same screen: "Desvincular password" mixes languages — the button label leaves "password" untranslated in pt-BR.
  - **Password policy**: owner asks whether to require a special character and a number on top of the 12-char minimum. Note before deciding: current NIST SP 800-63B guidance recommends *against* composition rules (they push users to predictable substitutions) — length + breached-password screening is the recommended posture. Needs an explicit spec decision either way (D-number amendment).
- **Timezone picker is free text** (owner, 2026-08-10): profile settings timezone field is a plain text input; should be a dropdown/combobox over the IANA zone list (searchable, localized display names — `Intl.supportedValuesOf('timeZone')` covers modern browsers), with validation against the same list the backend accepts.
- **Calendar (availability) view rework** (owner, 2026-08-10): current view is ugly, has bad UX, and offers no way to remove a time period marked as available — a functional gap, not just polish. Owner suggests evaluating the FullCalendar library (https://github.com/fullcalendar/fullcalendar — core is MIT; some plugins are paid "premium", check which features fall where before committing). Evaluate against: bundle size, i18n (pt-BR/es built-in), WCAG keyboard/SR support, and A-013 (no premature dependencies) — then a design pass before implementation. Deletion of an availability block may also need an API/domain check (does a delete endpoint exist?).
